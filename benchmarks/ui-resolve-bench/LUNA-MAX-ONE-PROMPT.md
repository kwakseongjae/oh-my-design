# Luna Max one-prompt comparison

## Purpose

This comparison is a reproducible public demonstration, not a shortcut around the 2.0.0 frontier gates. It answers a narrow question:

> With the same starter, prompt bytes, Luna Max runtime, permissions, and delivery budget, what does each installed UI skill produce?

The public package has two layers. The **one-prompt shootout** is optimized for inspection and sharing. The **Verified Skill Lift Track** repeats the same method over the hidden task suite and is the only layer eligible for a general skill claim.

## Two leagues, never one mixed ranking

### Portable Skill Lift

- no skill
- raw `DESIGN.md`
- Anthropic Frontend Design
- Taste Skill
- Impeccable prompt-only
- UI UX Pro Max
- oh-my-design portable apply skill

Only the installed skill may change. Vercel Web Design Guidelines remains a review-track tool and is not inserted into a creation ranking. Hook-enabled Impeccable, OmD repair harness, and OmD full harness do not belong in this table.

### Harness showcase

Harnesses may use their documented agents, hooks, browser loop, checkpoints, and persistent context. They are reported on a quality/time/token/intervention Pareto chart, not ranked as portable skills. OmD full harness must not receive a portable-skill winner badge from this track.

## Frozen execution contract

No provider cell may start until all unresolved fields in `plans/luna-max-one-prompt-v0.1.json` are pinned.

1. Record the immutable provider model selector, Codex runtime version/hash, auth route, and the exact native effort value. A UI display label such as “Luna Max” is insufficient for a public model claim.
2. Freeze the starter commit/tree, `DESIGN.md`, prompt bytes, task oracle, fonts, OS, browser, viewport set, locale, network policy, and tool permissions.
3. Refresh every third-party competitor from its official source, record commit, license, installer behavior, and skill tree hash, then freeze it. Never silently use the newest competitor only after seeing results.
4. Use serial execution, balanced arm order, one fresh workspace per cell, the same timeout, runtime-default temperature, and no primary retry.
5. Preview runs use three independent trials per arm. A Verified public comparison uses ten per task and the complete hidden-suite denominator.
6. Preserve every success, failure, timeout, raw response, product diff, screenshot, manifest, and evaluator result.

## Prompt design

The shootout prompt should be short enough to resemble an X/Threads request but precise enough to evaluate. It names the product audience, primary task, required states, and non-negotiable behavior; it does not prescribe a visual solution or name a competitor.

The public prompt is frozen before any arm runs. A separate hidden oracle defines protected behavior, responsive conditions, accessibility, known facts, unresolved facts, and any screenshot-fidelity target. The oracle is never included in the model-readable workspace.

A useful first prompt family is a stateful product surface rather than a decorative hero: one primary journey, a compact data relationship, empty/error/success states, and a narrow-screen decision boundary. This still produces an inspectable visual result while exposing whether a skill preserves functionality and hierarchy.

## What is scored

The headline keeps objective validity and visual preference separate.

- `UI-Resolved@1`: build and protected behavior, primary journey, design grounding, responsive/200% reflow, accessibility, evidence honesty, and task-owned fidelity all pass on the first run.
- `Reliability@3` for the public preview; `Reliability@10` per task for Verified.
- `Ship Preference`: blinded pairwise “Would you ship this?” review with ties and both-fail choices. Preview requires at least five practitioners; Verified requires ten.
- efficiency: wall time, input, cached input, output, reasoning output, provider-reported cost or pinned price-equivalent, tool calls, and unplanned human intervention.

An aesthetically preferred result that breaks the journey is shown but cannot become UI-Resolved. A functional result cannot receive synthetic taste points from a single LLM judge.

## Honest time and token reporting

Each arm publishes min, median, mean, max, IQR, and P90 for wall time and provider telemetry. Cached input and reasoning output remain separate. Failed and timed-out cells remain in total spend.

The shareable claim format is:

> Same frozen prompt and starter. Exact Luna Max selector `[model]`, native effort `[effort]`, three independent runs per portable skill, no manual edits and no retry. `[system]` reached UI-Resolved in `[x/3]` runs; median `[time]`, `[tokens]` provider-reported tokens. All outputs and failures are public.

“Built in N hours / M tokens” may describe one run only when it is explicitly labelled as that run. The comparison headline uses the median and shows the range. Long-term OmD R&D Tokens-to-Target is reported separately and must never be presented as the cost of generating the showcased UI.

## Publication ladder

1. **Internal calibration** — exact source and evaluator plumbing; no ranking.
2. **Public preview** — one prompt × seven portable arms × three runs; descriptive results and blinded gallery, no global-best claim.
3. **Verified task result** — one audited task × ten runs; task-bounded ranking only.
4. **Verified Skill Lift** — hidden suite, three model families, confidence interval and audit gates; eligible for the 2.0.0 frontier claim.

Losses, ties, ambiguous tasks, incomplete token coverage, attribution limits, and manual interventions are first-class rows in the public report. The comparison is useful only if another skill maintainer can reproduce it and point to the exact condition under which OmD won or lost.
