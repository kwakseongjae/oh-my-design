# Source-contract Reliability@3 canary — 1.9.721

This diagnostic tests whether the source-contract 0.2 repair transfers across three fresh fictional product tasks rather than succeeding on one favorable layout. The locked tasks vary domain, palette, content cardinality, identifier length, and grid density. None has prior model exposure.

All three provider-free raw baselines score 75/85. Accessibility and responsive are the complete false critical-gate set for every task, and the hash-locked baseline evidence is fully represented by the sealed source contract before provider execution.

The fixed order is orbital optics transfer, seed-vault accession, then audio-archive ingest. Each cell uses Codex with `gpt-5.6-luna`, high effort, a 720-second timeout, one product revision, no retry, and no replacement. Execution is checkpointed one new cell at a time.

A cell passes only at 85/85 with resolved UI, one product revision, one successful and zero failed static closures, zero user handoffs, proof compliance, and unchanged sealed inventory. Reliability@3 passes only at 3/3.

Inventory drift, a second product edit, failed static closure, or contract-proof noncompliance freezes the remaining cells. An objective UI failure may be recorded without freezing only when the lifecycle contract remains clean. The experiment is diagnostic only: it does not enter public ranking, establish provider superiority, or promote a 2.0 release gate by itself.

Preparation and admission are provider-zero. External execution requires a separately audited prepared root and the applicable egress authorization.
