# OmD 2.0 frontier stop conditions

This file turns the `1.9.x` train into a finite evidence program. Patch numbers
are experiment identifiers, not progress by themselves. A patch is valid only
when it contains a preregistered hypothesis, a frozen denominator, retained
success/failure evidence, and a decision that changes the next queue.

## Completion stop

Promote `2.0.0` only when every gate in `RELEASE-TRAIN.md` passes:

1. Verified Skill Lift: OmD is first or statistically tied for first.
2. Overall paired resolved-lift 95% lower bound is above zero with no material
   negative slice across at least three model families.
3. The full harness is Pareto non-dominated for resolved rate, elapsed time,
   and unplanned human intervention.
4. At least 24 hidden tasks cover creation, repair, state, responsive,
   accessibility, evidence/unknown, screenshot fidelity, open briefs, and five
   locales.
5. Verified rows have ten runs per task and downloadable failures/timeouts,
   manifests, and representative artifacts.
6. Blind review has at least ten practitioners and reports agreement, reversal,
   both-fail rate, and confidence intervals.
7. Independent task audit estimates fewer than 5% broken/ambiguous tasks.
8. Install → first resolved surface and seven-day reuse improve over 1.9.0
   without accessibility, evidence-honesty, or Builder regression.
9. Natural-language routing chooses the smallest capable workflow, specialists
   advise with evidence, one agent owns edits, and the consumer route is
   reverified.

The version number, calendar, number of commits, and amount of work completed
cannot substitute for these gates.

## Autonomous continuation rule

Continue through local implementation, deterministic tests, prepared runtime
matrices, approved benchmark-provider execution, frozen evaluation, reporting,
and the next bounded repair without asking the user to request each step.

Every new `1.9.x` experiment must name:

- the unresolved frontier gate;
- one bounded hypothesis;
- the exact candidate delta;
- the frozen task/model/runtime/budget denominator;
- success, guardrail, rollback, and first-failure rules;
- the result and how it changes the next experiment.

Do not create a patch for documentation churn, a rerun of the same denominator,
or work that produces no new gate evidence.

## Hard pause conditions

Pause for user direction only when:

1. a choice changes product positioning, public claims, pricing, data
   collection, or the benchmark's normative definition rather than merely
   implementing the locked protocol;
2. completion requires credentials, payment, publishing, production rollout,
   contacting people, or destructive repository/external-state mutation not
   already authorized;
3. two fresh bounded replacements fail for the same root cause after one
   tested repair, leaving materially different design directions;
4. the next gate requires the user's practitioner recruitment, production
   observation window, or access to a runtime/account that is unavailable;
5. all nine frontier gates pass, in which case stop before publishing or
   tagging `2.0.0` and present the final evidence package.

Auth/quota/network failures freeze the current denominator. They do not justify
retrying it; continue with local diagnosis and a fresh preregistered replacement
when possible.

## Standing transmission authorization

The user granted standing approval in the Codex conversation for benchmark
provider transmissions. It covers locked, prepared benchmark workspaces sent
to the named Codex/Cursor/Claude model runtimes for this 2.0 evidence program.

The authorization never includes credentials, secrets, unrelated user
documents, repository history, payment data, `web/public/llms-full.txt`, or
files outside each preregistered transmission boundary. A materially broader
payload remains a hard pause condition.
