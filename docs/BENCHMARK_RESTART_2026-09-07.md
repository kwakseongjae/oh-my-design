# 순정 포함 벤치 재시작안

상태: **실행 전 설계 초안**. 새 결과·순위·모델 우위 주장은 없다.
이 문서는 동결된 T3 프로토콜을 수정하지 않는다.

실행 모델·작업 순서·예산·완료 판정은 [통합 실행 계획](OMD_EXECUTION_PLAN_2026-09-07.md)의
B 트랙을 우선한다. 첫 회차는 Grok 4.6 단일 에이전트의 4조건 portable 비교이며,
calibration 4 + 본실험 36 + 후속 12셀이다. 전체 native harness 비교는 별도 선택 실험이다.
결과 집계 뒤 우선 결함 수정/회귀와 실제 비교 영상까지 B-6/B-7로 이어간다.

## 질문을 세 개로 나누기

1. **에셋 제작**: 같은 도구를 사용할 수 있을 때 각 스킬이 더 적합하고 일관된 에셋을 기획·생성·선택하는가?
2. **최종 화면**: 그 에셋을 사용한 최종 페이지를 사람이 실제로 더 쓰고 싶어 하는가?
3. **지속성**: 첫 결과 이후 같은 변경을 요청할 때 브랜드·동작·반응형을 더 잘 유지하는가?

세 번째가 OMD의 DESIGN.md·근거·상태 계약이 제공할 수 있는 가치다.
어느 한 축에서 이기지 못해도 다른 축을 측정할 수 있다. 문서가 길다는 이유로 승리시키지 않는다.

## 재사용할 코드

- 격리 준비: `benchmarks/ui-resolve-bench/scripts/prepare-sandbox.mjs`, `prepare-run-matrix.mjs`
- 실행/귀속: 같은 디렉터리의 `run-codex.mjs` 또는 `run-claude.mjs`, runtime/model attestation
- 객관적 결함: task별 evaluator + render/contrast
- 사람 선호도: `prepare-review-round.mjs`, `intake-review-round.mjs`, `aggregate-ship-preference.mjs`
- 반복/비용: `aggregate-results.mjs`, `run-record.schema.json`
- T3 재사용물: 공통 스냅샷, 결함 예시, 원본 입력 기록. 기존 점수는 새 회차에 합치지 않는다.

이는 기존 runner가 새 Hallmark/Aphrodite 조건을 이미 지원한다는 뜻이 아니다.
adapter·activation·도구 차단은 파일럿 전 preflight에서 확인해야 한다.

## 4개 조건

| 조건 | 허용 추가 컨텍스트 |
|---|---|
| no-skill | 공통 브리프·사실 자료·도구 사용 설명·host 기본 지시만 |
| uiuxpromax | 동일 입력 + 고정 revision의 해당 스킬 |
| hallmark | 동일 입력 + 고정 revision의 해당 스킬 |
| omd | 동일 입력 + 지금 평가하려는 배포 revision의 OMD |

완성된 공통 크리에이티브 에셋 세트를 제공하지 않는다. 모든 조건이 이미지·영상·로컬 제작 도구를
자유롭게 골라 자기 에셋을 생성한다. 공식 로고 같은 필수 사실 자료는 공통으로 제공할 수 있다.
모든 조건에 같은 host/runtime/model/reasoning·검증된 도구 접근 권한·생성/수정 예산을 적용한다.
도구를 사용할 권한이 같다는 뜻이며 실제 선택한 도구·생성 장수·에셋 모양은 같게 만들지 않는다.
호스트의 숨은 기본 지시가 같다는 의미의 통제군이며 모델의 순수 사전학습 능력 시험이 아니다.
no-skill만 도구를 빼거나 전문가가 다듬은 입력을 OMD에만 주면 실험 질문이 바뀐다.

현재 감사 세션은 이미 OMD 지시·결과물을 읽었다. 이 세션의 산출물을 순정 모델 결과로
명명하지 않는다. 각 셀은 새 workspace·새 세션에서 실행하고 전역/프로젝트 스킬·메모리·
hooks를 점검한다. 다른 셀의 결과나 점수를 생성기에 보여주지 않는다.

**스킬 효과와 전체 하네스 효과는 별도 회차다.** 스킬 회차는 추가 에이전트 없이 같은 도구에서
명시적 activation만 바꾼다. 미디어 도구 backend 모델은 host 하위 에이전트와 구별해 귀속을 기록한다.
네이티브 하네스 회차는 정상 orchestration을 허용하고 총 비용/시간/추가 호출을 함께 공개한다.
한 조건에만 이미지 생성 권한을 주면 통제 실패다. 동일 권한에서 한 조건만 이미지 생성을 선택하는 것은 유효한 결과다.

## 병렬 실행과 공유 브라우저

같은 과제·반복의 **Grok 4개 조건을 병렬** 실행한다. workspace/session/prompt/assets는 셀별로
분리하고 공통 브라우저 조작 구간만 **FIFO 1슬롯 broker**를 통해 직렬화한다.
탐색·생성 조작·다운로드·검증 capture 모두 같은 공유 browser lock을 거친다.
기다리는 조건에 다른 조건의 탭/결과가 노출되지 않아야 하며, 생성 요청과 다운로드는 셀 ID로 귀속한다.
작업이 끝나지 않은 browser lease를 timeout만 보고 재할당하지 않는다.
서비스가 안정적인 job ID/재수거를 지원하면 생성 대기 중 browser를 놓고 이후 수거할 수 있다.

`elapsed`, 실제 셀이 중단된 `broker_queue_wait`, `active`, `browser_use`, `media_service_wait`를 기록한다.
대기 중 코딩 등 다른 작업을 계속했다면 그 시간은 active다. 중첩되는 세부 시간은 합산하지 않는다.
active 상한·queue 상한·전체 elapsed 상한은 calibration에서 공통으로 동결한다.
병렬 결과의 속도는 descriptive-only이며 순수 모델 latency 순위로 사용하지 않는다.
브라우저 병목이나 rate limit이 나타나도 특정 조건만 다른 모델/도구로 바꿔 채우지 않는다.

## 최소 파일럿

처음에는 3개 과제 × 4조건 × 3회 = **36회**를 상한 후보로 잡는다.
먼저 별도 한 과제 × 4조건을 병렬 calibration하고, 입력/도구/격리/브라우저 결함이 없을 때 본실험을 실행한다.
이것은 준비용 표본이지 일반적 우월성을 주장하기에 충분한 표본이라는 뜻이 아니다.
calibration의 임시 상한은 사전에 명시하고, 본실험의 상한·모델/스킬 revision·도구 inventory는
calibration 후 본실험 전에 manifest로 동결한다. 미확정 값을
실행 완료 후 채워 넣거나 추정 비용을 관측 비용으로 기록하지 않는다.

| 과제 | 공통 브리프 핵심 | 결과 검사 |
|---|---|---|
| 신규 랜딩 | 가상 크리에이티브 제품, 가치 제안·실제 동작 CTA, 에셋 자율 기획·생성 | 에셋/최종 화면 각각 선호, 5초 제품 이해, CTA/모바일/키보드 |
| 국내 브랜드 맥락 | 동일한 원본 증거팩에서 근거 있는 표면 구현, 모르는 값은 발명 금지 | 근거 추종·unknown·브랜드 식별 가능성 |
| 기능 UI | 가상 예약/온보딩, 제공 데이터·성공/오류/빈 상태, 실제 동작하는 핵심 과제 | 과제 성공·모바일·접근성·제품 맥락 유지 |

후속 변경은 기능 UI의 12개 제출물을 동결한 뒤 같은 변경을 요청하는 **추가 12회**로 둔다.
첫 제출 36회와 합쳐 48회 호출이며, 후속 단계를 새 독립 과제로 세지 않는다.
필요하면 첫 제출 파일럿만 실행할 수 있지만, 그 결과로 후속 수정의 이점을 주장하지 않는다.
정확한 task/repetition 단위와 두 단계의 예산을 등록할 때 실행 범위를 확정한다.

## 평가

- 에셋-only 익명 패킷: 브리프 적합성·세트 일관성·눈에 보이는 결함·의미 있는 차별성, 해당 시 영상 연속성.
- 최종 페이지 익명 패킷: 에셋의 배치·카피 의미·가독성·동작·로딩/모션을 별도 평가.
- 에셋과 페이지는 독립 익명화하고 에셋 평가를 먼저 고정한다. 생성 장수·영상 유무 자체에 가점을 주지 않는다.
- 에셋이 필요 없는 UI는 해당 없음으로 기록한다. 과제가 요구한 에셋이 빠졌으면 누락 실패다.
- 생성 시도/실패/버린 후보/선택/실제 사용 목록·prompt·참조·tool/media model·SHA·사용 위치를 보존한다.
- 에셋 선호와 페이지 선호의 관계를 곧바로 인과로 해석하지 않는다. 고정 에셋 회차는 필요 시 별도 등록한다.
- 첫 제출과 최종 제출을 모두 저장한다. 최종 산출물 비교를 본표로, 수정 횟수/시간을 곁에 둔다.
- 기능·접근성·잘림·에셋 실패는 객관적 결함. 미적 선호로 상쇄하지 않는다.
- 시각 평가자에게는 같은 viewport/상태의 익명 화면만 준다. system.md·trace·스킬 이름을 숨긴다.
- 화면 선택과 문서 유용성은 별도 패킷/별도 평가다. 식별력은 원본 자극으로 먼저 교정한다.
- 최소 여러 실제 평가자의 선택과 사유를 받는다. 모델 평가는 보조 결함 탐색으로 쓴다.
- 과제별 반복이 독립 브랜드 표본을 늘리는 것은 아니다. task를 고려한 CI를 보고한다.
- 실패·timeout·재시도를 모두 분모에 남긴다. 최선의 한 장을 arm의 대표 성적으로 사용하지 않는다.
- CI가 0을 포함하거나 평가자가 합의하지 않으면 그 상태를 결과로 남긴다.

## 공개 소재

비교 영상: 공통 프롬프트/동등한 도구 → 각 조건의 생성 에셋 → 같은 크기의 최종 화면 →
실제 인터랙션 → 조건/재현 링크. 30~45초 본편과 10~15초 짧은 컷 2개를 만든다.
4열로 작게 줄여 글자가 안 읽히는 편집은 피한다.
전체 결과 gallery에는 반복별 대표·최선·최악과 미완료를 함께 둔다.

현재 사실로 가능한 각도는 “순정 모델과 세 스킬, 같은 입력의 결과를 직접 고르기”,
“예쁜 첫 화면 다음 수정에서 디자인이 유지되는가”다. 승리 숫자는 실행 후에만 정한다.

## 실행 전 남은 일

1. anchor model/runtime와 정확한 package revision 고정, 비교 스킬 activation adapter 확인.
2. 공통 입력·검증된 도구 inventory·예산·에셋 receipt를 준비하고 no-skill 오염 검사.
3. browser broker/셀 격리·4개 병렬 preflight, 에셋-only/페이지 reviewer packet과 동작 acceptance.
4. 4셀 preflight → 방법 결함 정정 → 새 manifest 동결 → 파일럿 실행.

이번 후속 작업에서 자유 에셋 생성·4조건 병렬 계약과 provider-zero 검증을 구현했다(17/17 PASS).
실제 browser broker/CLI adapter 연결과 calibration은 별도 검증 대상이며, 36회 생성은 아직 실행하지 않았다.
