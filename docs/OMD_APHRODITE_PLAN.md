# 아프로디테 스킬화 계획 (2026-09-04, r3 진행 중)

> 목표: "IT 회사든 디자인 스튜디오든 ERP 회사든, 자기 이미지셋을 넣으면 와우 페이지 한 장이 나온다."
> 채점 이력 Ninefold 30 → Higgsgen r1 60 → r2 70. 각 라운드의 실패 원인을 **규칙·검사기·라이브러리**로 굳혀 왔다.
> 이 문서는 그 결과를 스킬 형태로 고정하는 계획이다. 특정 브랜드·색·업종 전제는 넣지 않는다.

## 1. 와우는 층으로 쌓인다 — 라운드별로 확인된 순서

| 층 | 무엇 | 실패했을 때 증상 | 규칙·검사기 | 상태 |
|---|---|---|---|---|
| 0 구조 | 섹션 리듬·기하 | (없음) | 코덱스 LC-1~36 | 있음 |
| 1 밀도 | 채울 것이 있는가 | 휑함(빈 화면 7/12) | LI-24~26 · 밀도 예산(개수) | 있음 |
| 2 마감 | 서체·그레인·깊이·색보정 | "문서처럼 보임" | LC-37~47 · LI-27~32 · font-inline | 있음 |
| 3 스크롤 안무 | 이미지가 행동한다 | "이미지를 그냥 씀"(30→60) | 이미지 동사 1개 규칙 · scroll-gsap 레시피 9 | 있음 |
| 4 정착 타이밍 | 펼친 것을 볼 시간 | 종점 = 퇴장(70점 지적) | **LC-48 · LI-33** · scrub-timing-probe | 있음 |

## 2. 스킬 구조 (omd-aphrodite = landing 의 합격선 모드)

1. **채널 확인**(omd:setup) → 2. **서체 조달**(font-inline) → 3. **컨셉·스토리보드**(이미지 동사·유휴 동사·정착 대역·액센트 사건을 숫자로) → **3.5 게이트**(A~C, FAIL 시 중단) → 4. **에셋**(omd:media 배치, 접미사 반복, 참조 앵커) → 5. **빌드**(fx-library 스니펫 + scroll-gsap 인라인, 제로 베이스 금지) → 6. **검증**(render·contrast·landing LI-1~33·scrub-probe·콘솔 스크롤·390) → 7. **리뷰**(designer-review, BLOCK 0) → 8. **쇼케이스**(홍보 문법) → 9. **사용자 채점 → FEEDBACK.md 매핑 → 다음 라운드**.

업종 무관 보장: 스킬 본문은 역할·빈도·숫자만 말한다(색 이름·다크/라이트·업종 단어 없음). 이미지 id 는 세트 스펙의 변수. 브랜드 사실은 DESIGN.md 에서만.

## 3. 남은 작업 (우선순위)

1. **r3 채점 반영** → 90점까지 라운드 반복. 라운드마다 "규칙으로 굳힌 것"이 하나 이상 나와야 한다(안 나오면 그 라운드는 취향 조정이지 학습이 아니다).
2. **fx-library 정착**: INDEX 를 층(유휴/호버/스크롤) 구조로 유지, 신규 효과는 README+demo+snippet+라이선스+reduced-motion 3분류 필수. `omd fx list/demo` CLI 노출(설치본에서 라이브러리를 볼 수 있게).
3. **게이트 자동화**: storyboard-review 표를 스토리보드 파일에서 기계로 읽어 판정하는 `storyboard-gate.mjs`(지금은 사람이 채움).
4. **모바일 안무 규격**: 390 에서 핀 해제 시의 경량 안무를 코덱스 규칙으로(LC-49 후보).
5. **범용 브리프 3종 테스트**: IT 툴 · 디자인 스튜디오 · ERP 벤더 — 같은 스킬로 3장을 만들어 게이트·검사·리뷰가 업종에 상관없이 성립하는지 확인(품질 게이트 픽스처로 편입).
6. **릴리즈**: 위 5 가 통과하면 2.0.1→2.1.0(아프로디테·fx-library·게이트·검사기 LI-24~33·font-inline·image-batch). npm publish 는 사용자 요청 시.
