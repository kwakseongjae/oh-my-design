## Checker interactions (E3 reporting)

Both are `scripts/design-md-core-conformance.cjs` heuristics, not the migration gate, and both are reported here rather than worked around in silence.

1. **`no_prescriptive_placeholders` false positive.** A table cell whose entire content is the word `Unresolved` matches `BARE_PLACEHOLDER`, so an evidence-class table row labelled `Unresolved` reads as an emitted placeholder even when the row's own text says the item is not a token. The fix was to carry the §3 evidence classes in the source's own bullet form (`- **Unresolved:** …`), which is what the source uses and is strictly closer to it than the table was. No word changed.
2. **`actionable_foundations_or_known_constraints` false positive.** The heuristic `containsUnresolvedSemanticClaim` fires when `rule|foundation|constraint` is followed within 40 characters by `unresolved`. The source's own §15 pair — “… or reduced-motion **rule**. Motion tokens are **unresolved** and omitted.” — trips it, so a Foundations claim that is in fact full of measured colors, spacing, shape, and elevation values reads as a claim that the foundations are unresolved. The first sentence is carried verbatim; the second is carried as “No motion token is promoted, and every motion value stays absent rather than being filled with a plausible default.” That is the same disposition in the phrasing the approved bodies already use (`musinsa`: “No motion token is promoted”), and the unresolved motion fields are still named in Governance Named gaps. Recorded here because the wording choice is visible to the checker; the meaning is unchanged.
