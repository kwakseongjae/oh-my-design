# identity/CI 어휘 재조사 — 세 시장, 서로 다른 답 (2026-09-21)

확충 계획 4단계(로드맵 C6). §C.3의 시장별 상한은 **이 조사 전까지 잠정**이라고 문서 스스로
적어두었다. 한국에서 「디자인 시스템」 대신 "our identity / CI 가이드"로 다시 찾았더니 Tier 1이
0→4가 됐고, JP·TW·CN에는 그 패스를 돌린 적이 없었다.

세 시장에 하나씩, 병렬로 돌렸다. 원문 보고는 `docs/research/2026-09-21-vocabulary-resurvey/`
(비추적, 09-16 브리핑과 같은 관례).

## 결과

| | verified | 어디에 있나 | 민간 대기업 |
|---|---:|---|---|
| **JP** | 7 | 대학 · 지자체 · 중앙정부 · 행사조직 | **없음** |
| **TW** | 13 | 정부 · 대학 **전부** | **없음** |
| **CN** | 12 | 대학 5 + **민간 대기업 다수** | **있음** |

어휘 전환 자체는 세 시장 모두에서 통했다 — design-system 검색이 **구조적으로 볼 수 없는**
층이 실재한다. 그러나 **그 층이 어디에 있는지는 시장마다 다르다.**

## 나는 에이전트 인용을 믿지 않고 다시 받았다

13건을 직접 페치해서 인용된 값을 grep했다.

```
JP  u-tokyo #0B8BEE ✓   sophia #9A003D ✓   titech #005396 ✓   plateau #00BEBE ✓
TW  NCKU #420A15 ✓      NYCU Pantone286 ✓  NTCH Pantone1797 ✓(브라우저에서만)
    NTHU Pantone259 — 내 환경 DNS 실패, 미확인
CN  QQ #EA1C26 ✓        TencentCloud #00A4FF ✓  PKU R139 ✓  Donghua 7627 ✓
    小爱同学 #05C5FA — 403, 미확인
```

**10건 확인 · 2건 내 환경에서 도달 불가 · 0건 반증.** 미확인 2건은 **반증이 아니다.**

## 정정 하나와, 내가 낸 오류 하나

CN 에이전트가 요약 첫 줄의 카운트를 정정해 왔다(19/5 → **21 opened / 7 thin**; verified 12·
blocked 2는 불변, 표는 동일). **내 기록은 이미 12/7/2였다** — 헤더를 베끼지 않고 행을 셌다.

CN 에이전트는 또 둥화대 여백 비율을 `0.5a`로 낼 뻔했다가 **`0.2a`로 고쳤다**(텍스트 레이어가
`为 �.�a`로 깨져 있었다). 내가 PDF를 다시 읽었다 — **문서에 두 값이 다 있다.** `0.5a`는 다른
규칙에 붙어 있고 限制区域 섹션은 `0.2a`다. 정정이 옳다.

그걸 확인하다 **내가 오류를 냈다**: 파일 경로를 공백 없이 타이핑해 없는 파일을 읽었고,
`pdftotext`가 0줄을 내자 **원래 맞았던 확인을 철회할 뻔했다.** 더 나쁜 건 `2>&1 | grep -c`가
**1**을 반환한 것 — 파일명에 `7627`이 든 **에러 메시지**를 센 것이다. 경로를 고치니 `7627 C`가
144행에 그대로 있었다. **`2>&1`을 grep에 물리면 실패가 성공처럼 보인다.**

## 방법론 — 이번 조사의 가장 이식성 높은 산출물

**UA를 갖춘 curl로도 부족하다.** 기존 교훈은 "403은 대개 헤드리스 탐지"였는데 한 단계 더 간다:

- TW 에이전트: 자동 페치를 막은 **3개 호스트 전부 실제 브라우저에서 정상 렌더, 그중 2개가 find.**
  국가양청원·타오위안시는 curl만 썼으면 "도달 불가"로 적혔을 것이다.
- **내가 재현했다** — 국가양청원은 curl에 200을 주지만 본문이 JS 셸이라 `1797`이 없다.
  실제 브라우저로 렌더하니 나온다.
- CN: 텐센트 CDN은 **`Referer: https://isux.tencent.com/brands/`가 필요**하다. 없으면 403.
  이것도 재현했다.

→ **이전 패스들이 curl만으로 `blocked`를 적었다면 그 행들은 다시 열어야 한다.**

## 상한에 무엇을 하는가 — 두 종류를 섞으면 안 된다

카탈로그는 **아이덴티티 전용 레퍼런스를 이미 갖고 있고, 최상위 티어를 주고 있다**:

```
id       tier          components  interactive  stated  claims
krds     verified_v2           12            5       5     199   ← 진짜 디자인 시스템
toyota   verified_v2            1            0       0      34   ← 아이덴티티만
sony     verified_v2            1            0       0      23   ← 아이덴티티만
```

**JP·TW의 발견 20건은 toyota/sony 모양이 된다.** 대학·지자체 VI 매뉴얼에는 컴포넌트도
상태도 없다. count는 오르고 **평균 깊이는 내려간다.**

**CN은 다르다.** 텐센트 ISUX 브랜드북은 **제품 브랜드북**이다 — QQ·QQ空间·텐센트클라우드는
살아있는 제품 표면을 가진 제품이고, 브랜드북(토큰급 색·서체·최소 크기·금지사항)에 라이브
캡쳐를 더하면 **완전한 레퍼런스**가 된다. 하이얼·화웨이·샤오아이도 같다.

### §C.3 대비

| 시장 | §C.3 현실적 신규 | 이번 조사가 말하는 것 |
|---|---|---|
| JP | 115~160 (Tier 1 14~22) | 제품 레퍼런스 여력은 **안 바뀐다.** +7은 아이덴티티 도메인 |
| TW | **0 권장** | 제품 기준으론 0이 여전히 맞다. 그러나 **아이덴티티 층은 13건 + 미조사 다수** |
| CN | +30에서 중단 | **과소평가로 보인다.** 텐센트만 브랜드북 14권(4권만 열람), 하이얼·화웨이·샤오미는 기존 추정의 "11개 회사" 밖 |

**700은 지금 당장 바뀌지 않는다.** CN 상향 여지가 생겼지만 CN 결정은 "게이트 확장 후"였고
게이트는 어제 넣었다(`942c5067`). 커버리지가 확정되면 그때 다시 본다.

## 오너 결정 — 자세히

### 내 첫 설명이 틀렸다

나는 "선례는 toyota·sony 2건이고 의도였는지 사고였는지 모른다"고 했다. **재보니 31건이다.**

```
컴포넌트 ≤1 AND 인터랙티브 0  →  31건 / 440
그중 verified_v2             →  31건 (전부)
```

alipay · aws-cloudscape · bmw · brandi · class101 · clay · clickhouse · cursor · elastic ·
familymart-tw · ferrari · flex · hashicorp · hyundaicard · kbank · kream · millie ·
miricanvas · mongodb · ohouse · ollama · palantir · recruit · shinhanbank · softbank ·
sony · taishinbank · teamlab · toyota · upbit · upstage

**verified_v2 141건 중 31건(22%)이 이 모양이다.** 사고가 아니라 **이름 없는 계층**이다.

### 두 번째 정정 — 이들은 아이덴티티 *출처*가 아니다

toyota·sony는 **`product-surface` 라이브 캡쳐를 3건씩** 갖고 있다(`global.toyota/en/` 등).
컴포넌트가 1개인 건 증거가 PDF라서가 아니라 **토요타 글로벌 사이트가 원래 컴포넌트가
빈약한 마케팅 사이트**이기 때문이다.

**대학 VI 매뉴얼은 다른 물건이다** — 라이브 표면 관측이 아예 없는 PDF다. 두 개를 "얇다"로
뭉뚱그리면 안 된다.

### 그런데 게이트가 둘을 구분하지 못한다 — 이게 핵심이다

proof gate는 `.verification.md`에서 **원시 샘플 5개 이상**을 요구한다. 세는 방식이
`/rgb\(|#[0-9a-fA-F]{6}\b|\b\d+px\b/` — **hex 모양 문자열을 센다. 관측을 세지 않는다.**

상지대 VI 매뉴얼의 색값 5개를 산문에 옮겨 적으면:

```
raw samples counted: 5   (게이트 요구치: >= 5)
→ 라이브 관측 0회로 proof gate 통과
```

즉 **"이걸 넣을 것인가"는 이미 열려 있다.** 막는 장치가 없다. 결정해야 할 것은
**"넣을 것인가"가 아니라 "구분할 것인가"다.**

### 그래서 실제 선택지는 셋

| | 하는 일 | 대가 |
|---|---|---|
| **A. 그냥 넣는다** | JP+TW 20건 추가, 700에 빨리 닿음 | verified_v2가 "깊이"를 뜻하지 않는다는 사실이 **31→51건**으로 커진다. 뱃지가 더 약해진다 |
| **B. 안 넣는다** | JP·TW 재조사 수확 ≈ 0, CN만 남음 | **기존 31건은 그대로다.** 문제를 안 늘릴 뿐 안 고친다. 그리고 게이트가 안 막으므로 **다음 사람이 모르고 넣는다** |
| **C. 넣되 구분한다** | 깊이를 노출 — 매니페스트에 `componentCount`·`interactiveComponentCount`가 **이미 있다** | 표면 작업(뱃지/필터)과, 700을 "700건 중 N건이 컴포넌트 깊이"로 다시 말해야 함 |

### 내 추천: **C**

근거는 셋이다.

1. **문제는 입장이 아니라 라벨이다.** 31건이 이미 사용자에게 `Verified v2`로 보이는데
   그 뱃지는 "증거 그래프가 완전하다"는 뜻이지 "컴포넌트가 있다"는 뜻이 아니다. 사용자가
   그 차이를 알 방법이 지금 없다.
2. **B는 문제를 고치지 않는다.** 안 넣어도 31건은 남고, 게이트가 안 막으니 재발한다.
3. **비용이 이미 지불돼 있다.** `componentCount`·`interactiveComponentCount`가 매니페스트에
   발행되고 있다. 읽어서 보여주기만 하면 된다.

C를 고르면 700의 의미가 **정직해진다** — "700개"가 아니라 "700개, 그중 N개가 컴포넌트
수준의 깊이". 수요가 멱법칙(상위 10개 = select의 41.3%)이라 꼬리의 가치는 어차피 count가
아니라 **찾는 사람이 무엇을 받는지 아는 것**이다.

**내가 정하지 않는다.** C는 제품 표면(뱃지·필터·카피)을 건드리므로 오너 결정이다.
