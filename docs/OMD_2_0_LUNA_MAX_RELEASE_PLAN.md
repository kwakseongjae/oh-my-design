# OmD 2.0 Luna Max release plan

Status: **BLOCKED BEFORE PROVIDER EXECUTION**

## Model roles

The machine authority is
[`omd-2.0-model-role-routing-v0.1.json`](../benchmarks/ui-resolve-bench/config/omd-2.0-model-role-routing-v0.1.json).

- Planning, review, roadmap and the release decision use
  `gpt-5.6-sol / xhigh`.
- Product, runner and publication-preparation implementation uses
  `gpt-5.6-sol / medium`.
- The actual comparison cells use `gpt-5.6-luna / max`.

Planning and implementation runs never enter the benchmark denominator. Their
time and token use are reported separately from Luna generation cost. Model or
effort substitution, failed-cell retry and failed-cell replacement are all
forbidden. Provider execution remains at zero until the user sends the exact
activation phrase `ㄱㄱ` after preparation is complete.

This plan turns the remaining external-usefulness question into the final
2.0.0 release gate. A good-looking selected screenshot is not enough. OmD must
show repeatable product quality, stronger blinded ship preference, a useful
project design-system artifact, and an acceptable time/token/intervention
frontier under the same Luna Max prompt and workspace contract as competing
portable skills.

## Release question

With the exact same blank starter, prompt bytes, Luna selector, native `max`
effort, permissions, timeout and network policy:

1. Does OmD produce a working, responsive and accessible product surface more
   reliably than model-only?
2. Is OmD first or statistically tied with the strongest eligible portable UI
   skill?
3. Do blinded practitioners prefer to ship its screen and its design-system
   handoff?
4. Is the quality gain non-dominated after wall time, tokens and human burden
   are disclosed?

If any release gate fails, 2.0.0 remains blocked. The failure cluster becomes
the next bounded product patch; no failed cell is retried, replaced or hidden.

## Tracks

### A. Luna Max portable-skill comparison

Only the installed portable skill changes:

- model only;
- Anthropic Frontend Design;
- Impeccable prompt-only;
- UI UX Pro Max;
- Taste on eligible landing/marketing tasks only; and
- OmD 2.0 Autopilot.

The primary table never includes browser hooks, post-generation repair, OmD's
guided harness, task-specific DESIGN.md files, preselected references, hidden
components or candidate-specific examples.

### B. OmD harness Pareto

On the same three public showcase tasks, separately run OmD portable Autopilot
and the documented full harness. Report objective quality, blind preference,
wall time, provider tokens, tool calls, checkpoints and interventions. This is
a quality/cost frontier, not a skill-ranking row. The full harness cannot earn
the portable-skill winner label.

### C. Transfer confirmation

Luna Max is the primary showcase configuration. A release still requires a
nonnegative OmD direction on the locked Terra and Sol confirmation effort.
Model families are reported separately and are never pooled into one headline.

## Execution ladder

### Gate 0 — source and runtime seal

Before any provider call:

- commit the exact 2.0 candidate and require a clean worktree;
- publish and byte-verify all seven public Core schemas;
- refresh and freeze competitor commits, licenses, installers and tree hashes;
- bind task, prompt, starter, oracle, evaluator, browser, fonts and runtime;
- prove that Codex accepts exact `gpt-5.6-luna` + native `max` and records
  unambiguous model and usage telemetry;
- require a fresh workspace per cell, serial execution, retry zero and no model
  or effort fallback.

A failed preflight spends provider quota but starts zero benchmark cells.

### Gate 1 — Wow Preview

Run three public tasks spanning:

1. expressive consumer/brand surface;
2. dense operational state and recovery; and
3. mobile plus locale-sensitive flow.

Schedule: 3 tasks × 6 portable arms × 3 independent trials = 54 primary
cells, balanced and serial. Taste is marked ineligible rather than scored on a
non-marketing task. Preserve every success, failure and timeout.

The preview advances only when:

- OmD is UI-Resolved in at least 8 of 9 scheduled cells;
- all three tasks have at least 2 of 3 OmD successes;
- unsupported product facts, manual product edits, follow-up questions and
  unplanned interventions are all zero;
- OmD beats or ties the strongest eligible portable skill on objective task
  resolution;
- at least five blinded practitioners prefer OmD or tie it for ship choice on
  at least two of three showcase tasks;
- desktop, mobile and required-state screenshots are all publishable; and
- no competitor result is omitted from the gallery.

Failure blocks expansion and creates a bounded repair hypothesis. The existing
54-cell result remains immutable.

### Gate 2 — Release Qualification

After Gate 1 passes, run 12 hidden greenfield task families × 6 portable arms ×
5 trials. This is a maximum of 360 scheduled primary cells, with ineligible
arm/task pairs disclosed rather than backfilled.

Promotion requires:

- scheduled UI-Resolved rate at least 80%;
- Reliability@5 on at least 8 of 12 tasks;
- paired skill lift over model-only with confidence lower bound greater than 0;
- first or statistically tied with the strongest eligible portable skill;
- zero unsupported facts and 100% parseable design-system packages when a
  project system is warranted;
- nonnegative direction on Luna, Terra and Sol; and
- a non-dominated quality/human-burden/time/token result.

### Gate 3 — Blind launch review

Use at least ten practitioners. Labels and left/right order stay hidden, a
reversal subset is repeated, and ties plus both-fail are allowed.

Ask in this order:

1. Can the stated task be completed from this screen?
2. Would you ship this result?
3. Which result has clearer hierarchy and state legibility?
4. Which feels more distinctive and product-specific rather than templated?
5. Which design-system brief would you trust for the next screen?

Publish agreement, reversal inconsistency, pair counts and confidence
intervals. Synthetic personas or an LLM absolute taste score cannot replace
this gate.

## Scorecard and public evidence

`UI-Resolved@1` remains the primary gate. The diagnostic vector is reported but
never used to average away a functional failure:

| Dimension | Evidence |
| --- | --- |
| Product correctness | build, protected behavior, hidden journey, recovery |
| Responsive quality | 1440, 390, 320 and 200% reflow |
| Accessibility | axe, keyboard, focus, names and error association |
| Visual impact | blinded ship choice, hierarchy, distinctiveness, product fit |
| System quality | Core proof, provenance, state coverage, DESIGN.md-to-code conformance |
| Evidence honesty | unknown remains absent; unsupported facts are zero |
| Efficiency | wall time distribution, token classes, tool calls, intervention ledger |

Each public cell includes prompt, starter, exact skill/model/runtime hashes,
raw response, filesystem diff, desktop/mobile/state captures, evaluator result,
wall time, provider token telemetry and failure log. Headlines use the median
and show min/max, IQR, P90 and the full success denominator.

## Release decision

### Ship 2.0.0

Ship only when Gates 0–3 pass, public Core schemas are live and byte-identical,
the independent claim audit passes, and the complete downloadable evidence
package can reproduce every headline number.

### Hold and improve

Hold when OmD is visually generic, unreliable, model-sensitive, dominated on
cost/human burden, or loses the design-system trust comparison. Classify the
smallest recurring failure cluster, patch the product once, create a new
versioned preregistration, and rerun the complete affected denominator. Never
repair only the screenshot selected for marketing.

## Blog and launch package

The launch story is evidence-first:

1. **The same prompt, six systems, no hidden setup** — blinded desktop/mobile
   gallery with all failures.
2. **A screen is not a design system** — show the exact Core v2 DESIGN.md,
   provenance and code conformance behind the winning result.
3. **What the extra quality cost** — median time, token classes, tool calls and
   intervention Pareto for portable OmD versus the full harness.
4. **Where OmD lost** — publish failure clusters and the decisions that delayed
   release.
5. **Reproduce it** — downloadable task, prompt, starter, source hashes,
   evaluator and raw artifacts.

The viral asset should be a blinded slider/gallery that makes the visual
difference obvious, followed immediately by state, mobile and evidence proof.
Allowed copy is task-bounded: “On this frozen Luna Max comparison, OmD reached
X/Y UI-Resolved runs and received Z% blinded ship preference.” “Best UI skill”
or industry-wide superiority remains forbidden without the larger Verified
program.

## Immediate sequence

1. Finish and clean-commit the current Core v2 candidate.
2. Deploy the seven schema URLs and pass byte liveness.
3. Refresh competitor sources before seeing any new result.
4. Generate a fresh Luna Max preregistration bound to that commit.
5. Run the isolated selector/effort/telemetry preflight.
6. Execute the 54-cell Wow Preview serially.
7. Build the blinded gallery and collect five-person preview judgments.
8. If and only if the preview passes, execute the 360-cell qualification and
   ten-person launch review.
9. Run Terra/Sol transfer and independent claim audit.
10. Ship 2.0.0 and the evidence-backed blog, or publish a hold note and patch
    the smallest demonstrated weakness.
