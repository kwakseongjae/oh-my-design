## easywallet형이 지시를 뚫었다 — 지시가 아니라 층의 문제다

icook 결함은 웨이브 22 easywallet과 **정확히 같은 형태**다. 원본 YAML `:53`
`recipe-card: { … fg: "#564e4a" … }`가 산출 Homepage Story Card 블록(`:351–358`)에서
Text 행 없이 빠졌다. 같은 hex가 Search(`:331`)·Event card(`:367`)에 있으므로 문자열 grep은
「보존됨」으로 읽고, 게이트도 통과한다. 키 경로가 다르면 보존이 아니다.

**중요한 건 이 결함형이 이미 워커 지시에 있었다는 것이다.** 웨이브 29부터
「원본 YAML `tokens.*`의 모든 키 경로를 산출과 대조하라, 같은 숫자가 다른 스케일에 있다고
보존된 것이 아니다」를 명시했고 easywallet을 실사례로 붙였다. 그런데도 뚫렸다.

지시 문구를 더 강하게 쓰는 것은 답이 아니라고 본다. 워커가 **자기 산출물을 스스로 전수
대조**하는 데는 구조적 한계가 있고, 그것이 애초에 F3 층을 만든 이유다(웨이브 4 「같은 저자
맹점」). 실제로 이 건을 잡은 것도 다른 세션인 검토자다.

→ **제안: 키 경로 대조를 F3 조건절에 기계적 절차로 편입한다.** F3는 이미 원본과 산출을
파일 단위로 훑으므로, 원본 YAML `tokens.components.<id>.<field>` 각각이 대응 컴포넌트
블록에 행으로 존재하는지 확인하는 것은 자연스러운 확장이다. 워커 지시는 그대로 두되
(예방 효과는 있다) **검출 책임을 F3로 옮긴다**.
