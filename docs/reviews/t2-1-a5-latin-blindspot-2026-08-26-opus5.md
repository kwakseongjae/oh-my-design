# A5 copy-loss 게이트의 라틴 사각 — 코퍼스 44%가 무보호

**작성** 2026-08-26 · opus5 (오케스트레이터) · **발단** flex 이관 워커 보고

## 발단

flex 워커가 이관을 마치며 적었다: 원본 `DESIGN.md`에 비라틴 런이 **0개**라
`copy-loss` 게이트가 바늘을 하나도 만들지 않았고, **본문을 전부 의역해도 PASS가
나왔을 것**이다. 워커는 손으로 라틴 인용문 133개를 뽑아 42개 미생존을 찾았고 22개를
고쳤다. freee 워커도 같은 일을 했다(라틴 104개 추출, 0개 누락).

즉 두 워커가 게이트가 못 보는 자리를 각자 손으로 메웠다. 그건 다행이지만 **그 자리가
얼마나 넓은지는 아무도 재지 않았다.**

## 이 사각은 설계된 것이다

`migrate-reference.mjs`의 주석이 이미 이유를 적어 두었다. 바늘을 **연속 비라틴 런
4자 이상**으로 좁힌 것은 의도적 절충이다:

> 전체 인용문을 바늘로 쓰는 방식은 시도했다가 되돌렸다. legacy 파일은 카피만큼이나
> 설명을 인용한다(`Top utility nav (로그인 / 관심 / 최근)`). 전체 인용문 바늘은
> 발행된 적 없는 산문을 손실로 보고했고, 정작 그 안의 라벨은 살아 있었다.
> 늑대야 외치는 차단 게이트는 우회당하고, 그게 이 게이트가 막으려는 E3 실패 양식이다.

절충 자체는 옳다. 문제는 **절충의 대가가 얼마인지 숫자로 없었다**는 것이다.

## 실측

바늘 추출 로직을 그대로 코퍼스에 돌렸다 (같은 `QUOTED_COPY` 7형태, 같은 비라틴 4자 하한):

| | 수 |
|---|---|
| 레퍼런스 전체 | 440 |
| **바늘 0개 — A5 기계 무보호** | **195 (44%)** |
| 바늘 1개 이상 | 245 (중앙값 9, 최대 111) |

이관 완료본 125개로 좁히면:

| | 수 |
|---|---|
| 이관 완료 | 125 |
| **그중 무보호 상태로 통과** | **66** |

무보호 이관본에는 `apple` · `adobe` · `airbnb` · `claude` · `asana` · `airtable` ·
`aws-cloudscape` · `bbc` · `cashapp` 처럼 **영문 UI 카피가 브랜드 자산의 전부인**
레퍼런스가 몰려 있다. 카피가 곧 브랜드인 쪽이 정확히 무보호인 셈이다.

## 정정 — 사각은 195개가 아니라 440개의 라틴 절반이다 (2026-08-26 추가)

위 실측은 「바늘이 0개인 레퍼런스」를 셌다. 그건 **전면 사각**이고, 사각의 전부가 아니다.

웨이브 26의 `funnow`가 이를 드러냈다. 이 원본은 번체 중국어를 담아 바늘이 **12개** 잡혔고,
게이트는 `PASS`에 `unchecked`도 붙지 않았다. 그런데 워커가 자발적으로 라틴 전수 대조를
돌리자 **미생존 2건**이 나왔다 — 원본이 자기 슬로건에 붙여 둔 영어 gloss 두 개가 의역돼
있었다(`One-click booking online, head out instantly offline!` → 소문자화 + 느낌표 탈락).

바늘 12개는 비라틴 런에서만 나왔으므로 그 영어 문장을 **처음부터 보지 않았다.**

즉 정확한 진술은 이렇다:

| | |
|---|---|
| 비라틴 카피 | 게이트가 지킨다 (245개 레퍼런스에서) |
| **라틴 카피** | **440개 전부에서 무보호** |
| 바늘 0개 = 전면 사각 | 195개 (44%) — 이쪽은 `unchecked`가 이제 말해 준다 |

앞 절의 66건은 「A5가 **아무것도** 검사하지 않은 이관본」이고, 라틴 카피가 위험한
이관본은 **128건 전부**다.

이 정정은 조치의 우선순위를 바꾼다. 아래 2번(`unchecked` 보고)은 구현했으나 **전면
사각만 덮는다.** funnow 같은 부분 사각은 여전히 조용하다. 1번(절차)과 3번(소급 감사)의
범위도 66 → 128로 넓어진다.

보조 도구를 하나 만들었다 — `test-v2/tools/latin-copy-audit.mjs`. 원본과 sibling에서
인용 문자열을 뽑아 산출 3파일 생존을 대조하고 확신도별로 후보를 낸다. **게이트가 아니다.**
전체 인용문 바늘이 되돌려진 이유(설명문 오탐)가 여기서도 그대로 나타나서, 첫 보정 때
funnow 후보 11건 중 9건이 `Hero H1 headline on homepage` 같은 **카피에 대한 서술**이었다.
UI 메타 어휘 · 점 경로 · 폰트 스택을 걸러 후보를 11 → 2로 줄였지만 여전히 오탐이 남는다
(`freee` 0건은 워커 보고와 일치, `flex` 1건은 워커가 문서화한 콤마 하나 차이의 잔여와 일치).
숫자를 그대로 손실 건수로 읽지 마라 — **읽을 사람에게 후보를 주는 도구다.**

## `unchecked`의 임계값이 틀렸다 — furiosaai (2026-08-26 추가)

같은 웨이브의 `furiosaai`가 위 정정보다 한 발 더 나간 사례를 냈다. 워커의 보고:

> 게이트의 A5 검사는 기술적으로 살아 있었으나 사실상 눈이 멀어 있었다. 원본의 비라틴
> 바늘이 정확히 **하나**(`퓨리오사`)라 `unchecked`가 뜨지 않았고, 기계는 발행 문자열
> **181개 중 1개**를 비교했다. 손으로 돌린 라틴 스윕: **181 추출 / 27 미생존 / 26 복원 /
> 1 처분.**

내 `unchecked` 조건은 `바늘 == 0`이다. 바늘 하나면 조건이 거짓이 되고 경고가 사라진다.
**커버리지 1/181과 12/48과 20/90이 전부 「검사됨」으로 같은 얼굴을 한다.**

이건 내가 고친 그 실패의 재현이다 — 통과와 미검사를 갈랐더니, 이번엔 **전면 검사와
1% 검사**가 같은 화면을 쓴다. 이진 임계값으로는 못 잡는다.

고칠 방향: `copy-loss`가 바늘 수만이 아니라 **커버리지를 항상 출력**한다.
`needles=1 · candidates=181` 이 한 줄이면 워커가 자기 상황을 즉시 안다. 0인 경우의
`unchecked`는 그대로 두되(가장 심한 경우이므로), 부분 검사도 침묵하지 않게 한다.

**미구현.** 웨이브 26의 `fugle` 워커가 아직 게이트를 돌리고 있어서 하네스를 건드리지
않았다 — 워커가 검증하는 중에 하네스를 고치면 유령 실패가 난다(banksalad 전례).
fugle 완료 후 적용한다.

## 부수 발견 — sibling 미측정이 로그의 허위 서술로 굳었다

이 도구가 `friendliai`에서 우리 사이트 카피(`Browse 2,000+ AI-readable design systems`,
`friendliai — 0 DESIGN.md files | getdesign.md`)를 후보로 올려서 추적했더니, 출처는 오염이
아니라 **sibling의 Tier 2 교차검증 절**이었다. 정상적인 기록이다.

문제는 다른 데 있었다. `migrated/friendliai/migration-log.md:74`가 이렇게 적는다:

> `web/references/friendliai/` contains exactly one file, `DESIGN.md` (**checked with `ls`**).
> … that file does not exist in the repository.

**거짓이다.** `.verification.md`는 6,380 bytes로 실재하고, Tier 1 live inspect 20여 개
raw sample을 담는다. `ls`가 dotfile을 안 보여줬을 뿐이다 — 내가 finda 검증에서 저지른
것과 **같은 오류가 워커 쪽에서도 났고, 이쪽은 로그의 사실 서술로 굳었다.**

코퍼스 전수로 확인했다. 이관본 133개 중 sibling이 실재하는데 「없다」고 적은 것은
**friendliai 1건**이다. (내 첫 정규식은 4건을 올렸으나 셋은 오탐이었다 — `classting`은
오히려 "the sidecar file is present"라고 적었고, `flex`는 채택했으며, `fitpet`은 무관한
문장이었다. 계수 불일치를 결함으로 올리기 전에 두 번 세라는 규칙이 또 값을 했다.)

friendliai 개정을 발주했다.

## 무엇이 문제인가

A5는 "발행 문자열은 바이트로 옮긴다"는 조항이다. 게이트가 있는 45%에서는 기계가 이를
강제하고, 없는 44%에서는 **워커의 성실성만이 강제한다.** 그런데 A5 조항 자체가 생긴
계기가 바로 워커가 성실하지 않았던 사건이다 — 웨이브 19에서 datadog이 검증 카피 6종을
의역하고(`SEE THE PLATFORM` → "inspect the platform") dcard가 번체 포럼명 9종을 영문
의역으로 갈아치웠다. 그 두 건은 **비라틴이라서** 나중에 기계로 잡혔다.

라틴 전용 원본에서 같은 일이 일어났다면 지금도 모른다.

## 게이트를 넓히면 되는가 — 아니다

전체 인용문 바늘은 이미 시도되고 되돌려졌다. 되돌린 이유(설명 산문의 오탐 →
차단 게이트 우회 → E3)는 지금도 유효하다. 라틴 인용문에는 비라틴 런 같은
"우연일 수 없다"는 성질이 없어서, 정밀도를 되찾을 값싼 신호가 없다.

현실적인 방향 셋:

1. **워커 절차로 승격.** 지금 flex·freee 워커가 자발적으로 한 것(라틴 인용문 전수
   추출 → 생존 대조 → 미생존 처분)을 **무보호 브랜드에서 필수 단계로** 규칙집에 적는다.
   기계가 못 하면 절차가 하되, 절차가 있다는 사실이 문서에 남아야 한다.
2. **무보호 여부를 게이트가 스스로 보고.** `copy-loss`가 바늘 0개일 때 조용히 PASS하지
   말고 `copy-loss: 바늘 0 — 이 브랜드에서 A5는 기계 검사되지 않았다`를 **출력에
   남긴다.** 통과와 미검사가 같은 화면으로 보이는 게 지금의 실제 위험이다.
3. **소급 감사 66건.** 이미 이관된 무보호 66건에 라틴 전수 대조를 돌린다. R2 개선
   트랙에 넣는다.

2번이 제일 싸고 즉효다 — 통과와 미검사를 구별하는 것만으로 워커가 자기 상황을 안다.

## 상태

**2번 구현됨** (2026-08-26). `gateTexts`에 `problems`와 별개인 `unchecked` 채널을 뒀다.
바늘이 0개면 게이트가 조용히 PASS하지 않고 이렇게 답한다:

    { "brand": "apple", "verdict": "PASS", "problems": [],
      "unchecked": [ { "check": "copy-loss",
        "detail": "원본에 비라틴 런이 없어 바늘이 0개다 — 이 브랜드에서 A5는
                   기계 검사되지 않았다. 발행 라틴 문자열을 손으로 전수 대조하라." } ] }

`verdict`는 건드리지 않는다. 미검사는 결함이 아니므로 차단하면 안 되고, 다만 **보이지
않으면 안 된다.** 자기검사에 두 케이스를 넣었다 — 라틴 전용 원본은 반드시 보고하고,
비라틴이 있으면 보고하지 않는다. 12/12 통과. 실측 확인: `apple`·`flex`는 보고,
`flo`(한국어 카피 7종)는 미보고.

남은 것:

- **1번** — v10 후속 조항 후보(**A5a — 라틴 전용 원본에서 절차가 기계를 대신한다**).
  미착수. flex·freee 워커가 자발적으로 한 절차를 규칙집에 명문화하는 일이다.
- **3번** — 이관 완료 무보호 66건 소급 감사. R2 개선 트랙.
