# 워커 운영 계획 — Codex gpt-6.1-sol · Sonnet 5.5 · Opus (2026-10-29)

오너 요청(10/29): Codex Plus 크레딧으로 gpt-6.1-sol을 최대 effort 워커로 돌려 hangul·DESIGN.md 확충을 처리한다. 기획은 Opus가 맡고, 워커는 필요에 따라 Sonnet 5.5 medium이나 6.1-sol 최대 effort를 쓴다. 나중에는 DESIGN.md와 사이트 분석을 MCP로 제공하는 방향까지 기획한다.

## 0. 결론

- **가능합니다.** gpt-6.1-sol은 이 계정에서 `codex exec`로 effort `max`와 `ultra`까지 돕니다. 10/25에는 같은 호출이 'ChatGPT 계정 미지원'으로 거절됐습니다.
- **막히는 곳은 하나입니다.** Codex 샌드박스(workspace-write)에서는 네트워크와 웹 검색은 되지만 Chrome이 뜨지 않습니다. DESIGN.md 측정은 브라우저가 필요하므로, 측정 스크립트를 샌드박스 밖의 MCP 도구로 붙입니다. 시험으로 확인했습니다. 워커에게 전체 권한을 줄 필요는 없습니다.
- **워커 결과는 Opus가 검수한 뒤에 들어갑니다.** 워커는 커밋하지 않습니다.
- 시험 결과는 §2에 있습니다. 구현 파일럿 결과물은 검수를 거쳐 hangul 브랜치에 들어갔습니다(`7c0af0e7`).

## 3. 역할 분담

| 역할 | 맡는 일 | 맡지 않는 일 |
|---|---|---|
| **Opus(본 세션)** | 기획, 작업 지시서, 판정(분리 판정·헤드라인 재측정), 검수·커밋·푸시, 오너 보고 | 반복 구현, 대량 조사 |
| **gpt-6.1-sol (max)** | 판단이 섞인 긴 작업: 1차 사실·출처 조사, 대조군 판정, 정적 토큰 조사, 설계가 섞인 구현, 교차 계열 채점, 대량 반복 작업 | 머지·푸시, 오너 결정, 레퍼런스 최종 판정 |
| **Sonnet 5.5 (medium)** | 범위가 분명한 작은 구현(파일럿 H에서 4배 빠름), 짧은 생성, 브라우저 프로브(기존에 검증된 역할), 한국어 생성 평가의 작성자 | 저작 최종본(4회차에서 채택 안 함) |

- **effort.** 설계가 섞인 구현과 조사는 `max`, 단순 반복은 `high`. `ultra`(자동 위임)는 하위 작업을 Codex가 스스로 쪼개 크레딧이 더 들고 통제가 줄어서, 큰 단일 작업에서 따로 시험한 뒤에 씁니다.
- **계열 분리.** 평가에서는 작성자와 채점자를 다른 계열로 둡니다(같은 계열 채점은 점수를 부풀린다는 연구, R9-research.md).
- **한도 분산.** 10/25에 Claude 계정 세션 한도로 평가가 2시간 멈췄습니다. 대량 작업을 Codex로 옮기면 두 한도를 나눠 씁니다.

## 4. Codex 워커 운영 방식

1. **작업 지시서 한 장.** 목표, 범위, 하지 말 것, 검증 명령, 보고 형식을 적습니다. 레포 작업이면 AGENTS.md가 자동으로 읽히므로 규칙을 되풀이하지 않습니다.
2. **실행.**
   - 작업 하나에 워크트리 하나를 씁니다.
   - 실행 옵션은 `codex exec --ignore-user-config --json -m gpt-6.1-sol -c model_reasoning_effort="max" -s workspace-write -c sandbox_workspace_write.network_access=true -c approval_policy=never --output-last-message <보고>`입니다.
   - 이벤트 로그(JSON)와 마지막 메시지를 실행 폴더에 남깁니다.
3. **감시.**
   - 종료 표식(exit-code)을 기다리고, 로그가 15분 넘게 멈추면 멈춤으로 판정합니다(codex-fleet 전례).
   - 작업마다 시간 상자를 둡니다(조사 45분, 구현 60분).
4. **검수(Opus).**
   - 차이 읽기 → 검증 명령 재실행 → 게이트 → 커밋.
   - 설계 결함이면 `codex exec resume <세션>`으로 피드백해 반려합니다.
   - 워커 보고의 가장 강한 주장 하나는 반드시 다시 확인합니다(DESIGN.md 파이프라인의 ②′ 규칙).
5. **브라우저: 워커 전용 일반 Chrome.**
   - 10/29 시험에서 헤드리스는 SBB 빈 화면·Odoo 403이었고, 화면 있는 일반 Chrome + 로그인 없는 새 프로필은 정상이었습니다.
   - 그래서 워커 브라우저는 개인 프로필이 아니라 전용 프로필로 둡니다. 개인 계정 로그인은 금지하고, 로그인이 꼭 필요한 사이트는 이 용도로 만든 계정만 씁니다.
   - 그래도 막히는 사이트는 지금처럼 본 세션이 개인정보 규칙 아래에서 처리합니다.
6. **시각 근거(스크린샷·스크롤 영상).**
   - 레퍼런스마다 뷰포트·전체 페이지 스크린샷과 짧은 스크롤 영상을 남기고, 측정한 컨트롤은 상태별 크롭(rest·hover·focus·pressed)을 남깁니다.
   - 본 세션의 헤드라인 재측정을 '이미지로 대상 확인'으로 줄일 수 있습니다. 9/26 위임 스윕의 오류 3건이 모두 다른 요소를 잰 것이었습니다.
   - 크기는 SBB 기준 약 5MB입니다. 700건이면 수 GB이므로 git 밖(로컬 저장소 + 필요하면 클라우드)에 둡니다.
   - 사이트 게재는 정책(썸네일 크기, 캡처 날짜, 원문 링크, 삭제 요청 경로)을 정한 뒤 오너가 결정합니다.
7. **측정 도구 연결.**
   - 샌드박스 밖 `omd-probe` MCP 서버로 고정된 측정 도구만 엽니다: 페이지 조사, 키보드 상태 프로브, 컴포넌트 프로브.
   - 임의 스크립트 실행 도구는 만들지 않습니다. 그 순간 샌드박스가 의미를 잃습니다.
8. **동시 실행.** 2~3개로 시작합니다. 작업당 토큰 사용량을 이벤트 로그에서 재서 늘릴지 정합니다.

## 6. MCP 방향 (기획)

- **배경.**
  - 첫 커넥터(v1)는 2026-07-14 Core v2 전환 때 퇴역했습니다(`/api/mcp`는 410, npm `oh-my-design-mcp` 보관).
  - 성장 계획(10/13)은 AI 인용 채널로 MCP 커넥터를 다시 적어 두었습니다.
- **제안: v2는 두 층.**
  - **원격, 읽기 전용(Vercel).** 카탈로그 검색, DESIGN.md 조회(섹션·토큰 단위), 비교. 데이터가 정적이라 비용이 거의 없습니다.
  - **로컬(npx).**
    - 사이트 분석 `analyze_site(url)`: 사용자 컴퓨터의 Chrome으로 측정하고, 증거 묶음과 DESIGN.md 초안을 돌려줍니다.
    - 한국어 검사 `check_korean_copy` · `check_korean_typography`.
    - 측정을 사용자 쪽에서 하므로 서버 비용과 차단 위험이 우리에게 오지 않습니다.
- **씨앗.** 워커용 `omd-probe` MCP가 `analyze_site`의 첫 버전입니다. 내부에서 먼저 쓰며 다듬은 뒤 공개합니다.
- **수요 확인.** 만들기 전에 다음 두 가지를 봅니다.
  - 퇴역 뒤에도 들어오는 `/api/mcp` 요청 수(410 응답).
  - 상세 페이지의 봇·AI 요청 추이(월 8.9천 건, AGENTS.md).

## 8. 오너 결정

1. **워커 브라우저.**
   - 권장은 일반 Chrome의 워커 전용 프로필(개인 계정 로그인 금지)을 샌드박스 밖 캡처 도구로 쓰는 방식입니다.
   - 작업 중에 Chrome 창이 화면에 뜹니다. 거슬리면 나중에 별도 macOS 사용자나 다른 기기로 옮깁니다.
   - 다른 길은 개인 프로필을 쓰는 것인데, 권하지 않습니다(§4.5).
2. **시각 근거.** 스크린샷·스크롤 영상·컨트롤 상태 크롭을 내부 검증용으로 먼저 쌓을지. 사이트 게재는 정책을 정한 뒤 따로 정합니다.
3. **effort 기본값.** 구현은 Sonnet medium을 기본으로, 조사·판단은 6.1-sol max로 할지. ultra는 큰 단일 작업에서 따로 시험합니다.
4. **MCP v2 착수 여부와 순서.** 원격 읽기 전용부터 할지, 로컬 사이트 분석(캡처)부터 할지.
5. **동시 워커 상한.** 크레딧 사용량을 보고 정합니다.
