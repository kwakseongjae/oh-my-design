## 0. 오너가 정해야 할 것 — 계획보다 먼저다

### 결정 1. 목표 숫자

내 이전 분석(로드맵 §C.3)이 **현재 증거 기준을 유지하면 CJK 단독 상한은 630~710**이라고
적어두었다. 서 있는 목표는 "안정적으로 1000까지"다. 둘이 맞지 않는다. 내가 조용히 목표를
바꾸지 않고, 도달 못 한다고 문서에 적어둔 숫자를 향해 계획을 세우지도 않겠다.

| | 도달점 | 대가 |
|---|---|---|
| **(a) 1000 유지** | 1000 | Tier 3 볼륨 또는 비-CJK 확장. 게이트가 비싸게 만들고 **증거 깊이가 얕아지는 구간**에 들어간다 |
| **(b) 증거 기준 유지** | **630~710** | 숫자를 못 채운다. 대신 레퍼런스 한 건의 방어력이 유지된다 |
| **(c) 목표 재정의** | 커버리지 품질 | "몇 개"가 아니라 "어느 시장을 어느 깊이로". 마케팅 문구를 다시 써야 한다 |

**추천: (b) 또는 (c).** 이유는 경쟁 지형이다(§C.1). getdesign.md는 566건인데 **CJK가 0건**,
refero는 1,290건, `getdesign.kr`은 KR 21건으로 새로 등장했다. **볼륨은 이제 복제 가능하다.**
해자를 "CJK를 한다"에서 **"깊이와 증거로 한다"**로 옮겨야 하고, 그러면 1000은 해자가 아니라
비용이다.

⚠️ 630~710도 **잠정치**다. KR에서 "design system" 대신 **"identity/CI" 어휘로 재탐색**했더니
Tier 1 여력이 0에서 4로 바뀌었다. JP·TW·CN은 그 재탐색을 아직 안 했다(→ 4단계).

### 결정 2. CN을 키울 것인가

CN은 현재 5건이고 공급 여력은 +30이다. 그런데 **CN만 proof gate 밖에 있다**(아래 2단계).
그리고 로드맵 §7이 남긴 미확인 사항 — CN 사용자가 `/builder`에 **도달 가능한지** 확인되지
않았다. 공급은 yes, 유입은 unknown이다. 게이트를 고치기 전에 CN을 키우면 **검사받지 않은
레퍼런스를 30건 추가**하게 된다.

## 1. 기존 440은 어떤 기준으로 선정됐나 — 정직한 답

**절반 이상은 기록된 선정 근거가 없다.** `added` 필드가 **440개 중 244개(55%)에서 null**이다.
언제 왜 들어왔는지 레지스트리가 모른다. 사후에 규칙을 지어내지 않겠다.

실제 구성은 규칙이라기보다 **만든 사람의 시장**을 반영한다:

```
KR 203  US 109  TW 63  JP 43  UK 12  CN 5  IT 2  FR 2  DE 1
```

인증률은 그 편중과 따로 논다 — KR 67/203, US 44/109, **TW 10/63**, JP 13/43, UK 1/12.
**TW는 가장 세 번째로 크면서 가장 얇다.**

기록이 남은 것은 2026-06(153건)과 2026-07(43건) 두 번의 배치뿐이다.

### 명시적으로 결정돼 있는 기준 (CJK_EXPANSION_CANDIDATES, 2026-09-17)

1. **브랜드의 제품 디자인 언어만. 컴포넌트 라이브러리는 안 된다.** 1차 조사가 12개 중 10개를
   OSS 라이브러리(Arco·Semi·Vant·TDesign…)로 가져왔고 **범주가 틀렸다.** "ByteDance가 Arco를
   발행한다"는 Douyin이 어떻게 생겼는지 알려주지 않는다. 라이브러리는 **남의 브랜드를 담도록
   설계된 중립 도구**라 레퍼런스의 목적과 정반대다. 별도 트랙 가치는 있으나 같은 목록에 두면
   카탈로그의 주장이 흐려진다.
2. **Tier 1 공식 표면 필수.** 브랜드가 스스로 발행한 것.
3. **제품·마케팅·기업 표면은 별개 증거 도메인.** 한쪽 관측이 다른 쪽 토큰을 채우지 못한다.
4. **발행된 증거 > 볼륨.**

이 넷이 앞으로의 선정 루브릭이다. 새로 만들 필요 없다.

## 2. 지금 막혀 있는 것 — 확충은 시작할 수 없다

로드맵은 **5단계 "신규는 Core v2로 직접 작성"에서 확충이 열린다**고 적었다. 오늘 그 단계를
실제로 시험했다. **막혀 있다.**

`readReferenceSource`는 Core v2 문서를 만나면 `.omd/system/graph.json`의
`extensions["dev.oh-my-design.migration"].original_segments`에서 **legacy 바이트를 복원**한다.
그건 *마이그레이션 산물*이다. **처음부터 Core v2로 쓴 레퍼런스에는 없다.**

스크래치패드에 네이티브 Core v2 레퍼런스를 하나 만들어 돌려봤다:

```
THROWS: no preserved original segments. This package cannot reproduce the legacy
        source, so the reference's catalog metadata is unrecoverable from it.
```

**오늘 게이트를 통과시킨 리더 12개 전부가 여기서 던진다.** 조용히 비는 게 아니라 빌드가
죽는다(그건 낫다) — 그러나 **신규 레퍼런스를 한 건도 만들 수 없다**는 뜻이다.

원인은 Core v2가 **카탈로그 필드를 모델링하지 않기** 때문이다. country·category·added·
`verification_v2` 증거 그래프는 디자인 시스템의 속성이 아니라 카탈로그 엔트리의 속성이다.
지금까지는 legacy 복원이 그 구멍을 메웠다. 네이티브에는 메울 것이 없다.

> 오늘 만든 write gate는 **마이그레이션된 패키지**를 받는다. **네이티브 패키지는 아무도 안 받는다.**

## 3. 순서

세 결정 중 무엇을 고르든 **1~4단계는 동일하다.** 그래서 결정을 기다리지 않고 1단계를
시작할 수 있다.

| # | 할 일 | 왜 이 순서인가 |
|---|---|---|
| **1** | **Stage 5 해제** — Core-네이티브 증거 경로 | 이게 없으면 신규 560건이 전부 `partial`이 아니라 **빌드 실패**다. 카탈로그 필드(country/category/added)와 `verification_v2`를 Core 패키지 안에서 1급으로 표현하고, `readReferenceSource`가 네이티브를 받게 한다 |
| **2** | **proof gate를 CN까지** | `REGIONAL_PROOF_COUNTRIES = {KR, TW, JP}` — **CN만 빠져 있다.** 5건이 검사 없이 통과 중이고, 확충은 이걸 35건으로 만든다. 게이트 밖에서 늘리면 나중에 못 되돌린다 |
| **3** | **분류 체계 정리** | `ecommerce`(43) vs `e-commerce`(2), `fintech`(61) vs `finance`(1), 1~2개짜리 카테고리 8개. **더러운 분류에 루브릭을 적용하면 더 더러워진다.** 440을 먼저 고친다 |
| **4** | **탐색 어휘 재조사 (JP·TW·CN)** | KR이 "identity/CI" 어휘로 0→4가 됐다. §C.3의 시장별 숫자는 **이 재조사 전에는 확정이 아니다** — 문서 스스로 그렇게 적고 있다 |
| **5** | **1차 웨이브 3건** — Serendie + PayPay + AntUI | 네이티브 경로로 **끝까지** 한 번 통과시킨다. 리더 전부·게이트 전부. 규모를 키우기 전에 1단계가 실제로 동작하는지 증명 |
| 6 | JP 깊이 → CN ~30 → KR 편중 해소 | §C.3 순서. TW는 신규 0 권장, 예산을 **깊이로** 돌린다(10/63이 인증됨) |

**1차 웨이브를 Serendie로 여는 이유**: 직접 재측정했다. 라이브 DOM, 커스텀 프로퍼티 572개,
상태 전부(`rest #0650a0` / `hover·pressed #024288` / focus outline), 자체 GitHub 조직,
테마 다섯이 일본 전통색(浅葱·紺青·栗皮·菫·躑躅). **카탈로그가 원하는 종류의 브랜드 사실이
이미 구조화돼 있다.** 네이티브 경로의 시험대로 가장 좋다.

### 운영 방식

기존 `scripts/wave-run.mjs`를 쓴다 — 브랜드마다 워커 → 게이트 → F3 → 기계검사 → 검토 →
(개정 → 재실측) 체인을 독립 실행하고 동시 실행 수만 예산으로 묶는다. 층 단위 직렬 실행은
웨이브 44에서 사고를 냈다(같은 브랜드에 검토와 개정 동시 투입). **웨이브당 5브랜드**,
16-wide는 서버 레이트리밋에 걸린다.

방법론 정정 하나는 이미 전달돼 있다: **403은 대개 헤드리스 탐지다.** 막힌 10개 중 8개가
일반 브라우저 신원으로 200이 됐다. 재시도 없이 blocked로 적으면 천장을 실제보다 낮게 잡는다.

## 4. 병행 — 죽은 인용 8건 (마감 있음)

확충과 경쟁하지 않는 작은 항목. 11st · banksalad · brandi · hyundai · kream · kurly ·
onestore · patternfly는 **가장 먼저 만료되는 출처가 404**다. 죽은 URL은 "안 변했다"고
확인될 수 없으므로 **1월에 `partial`로 떨어진다.** 살아있는 대체 페이지를 찾아 재캡쳐하고
출처를 옮기면 된다. 8개 레퍼런스, 8개 URL.

## 요약

- **선정 기준**: 기존 440의 55%는 **기록된 근거가 없다**. 앞으로의 루브릭은 이미 정해져 있다 —
  브랜드의 제품 디자인 언어만, 라이브러리 제외, Tier 1 필수, 증거 도메인 분리.
- **막힌 것**: 네이티브 Core v2 레퍼런스는 **모든 리더가 던진다.** 확충은 여기서 시작한다.
- **정해야 할 것**: 목표 숫자(1000 / 630~710 / 커버리지) 와 CN 확대 여부.
- **결정과 무관하게 지금 할 수 있는 것**: 1~4단계.
