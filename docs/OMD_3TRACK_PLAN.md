### C7 판정 — 쿠팡 유지 (2026-08-22)

쿠팡은 시맨틱 랜드마크가 하나도 없다(`<header>`·`[role=banner]`·`<nav>` 전무, 전부 div).
크롬 필드가 비었던 건 채널 문제도 사이트 거절도 아니고 **수집기가 크롬을 시맨틱으로
찾고 있었기 때문**이다. 히어로 검출은 "클래스명은 거짓말하고 기하는 안 한다"로 짜놓고
크롬만 태그 이름을 믿고 있었다.

기하 검출로 바꾼 뒤:

| 필드 | 값 |
|---|---|
| header | 기하 검출, 70px, 렌더 배경 `#ffffff` |
| pageBackgroundRendered | `#fefefe` |
| primaryButton | `null` — **단, 해석 가능**: `buttonCandidatesAboveFold: 0` |
| typeScale | h2 24/700 · h3 20/400 · p 11/400 |

**유지 근거**: 크롬 3필드 중 2개가 채워졌고, 남은 하나의 부재는 사유가 함께 기록된다.
"페이지에 주 버튼이 없다"와 "수집기가 못 봤다"가 구분되므로 비교에서 쓸 수 있다.

### T3-1 유도 규칙의 핵심

프롬프트는 자유 작문이 아니라 **템플릿 + 근거 슬롯**이다.

```
[매체] [종횡비=evidence.imagery.aggregate.aspects]
피사체: <새로 정의> — 프레임 내 위치 evidence.imagery.aggregate.subjectCenter
노출: 다이내믹 레인지 evidence.imagery.aggregate.dynamicRange,
      평균 휘도 evidence.imagery.aggregate.meanLuma
톤: evidence.chrome.pageBackground 위에서 읽히도록
금지: 로고·워드마크·실제 제품명·타사 카피
```

**슬롯이 비면 그 문장을 쓰지 않는다. 대체 근거를 지어내지도 않는다.**
subjectCenter가 없으면 위치를 지시하지 않을 뿐이고, 그 자리에 "엣지투엣지" 같은
해석을 끼워 넣지 않는다 — 그 해석은 측정이 뒷받침하지 않는다.

`luminanceGradient`는 **조명 슬롯에 쓰지 않는다.** 그것은 화면 절반의 평균 휘도 차이지
광원 방향이 아니다.

### T3-6 비교 — 레인 두 개로 쪼갠다

검토 A와 B가 **독립적으로 같은 결론**에 도달했다: "핸디캡 없음·최대 강도"와
"동일 채널 고정"은 한 실험에 같이 걸 수 없는 배타적 가설이다.

Impeccable의 asset producer는 승인 목업 크롭에 대한 **image-to-image**가 본업이고,
hallmark의 이미지 계층은 typography → CSS/SVG → 외부 생성기다. 셋을 grok imagine에
고정하면 "지시문 품질" 실험이지 "스킬 최대 강도" 실험이 아니다.

| | 레인 A — Controlled | 레인 B — Native |
|---|---|---|
| 입력 | 동일 브리프 + **동일 스냅샷** | 동일 브리프 + 동일 스냅샷 |
| 경로 | grok imagine 고정, 동일 예산 | 각 팩의 네이티브 워크플로 허용 |
| 측정 | 지시 품질 (근거 추종) | 스킬 전체 능력 |
| 주장 범위 | "같은 근거·같은 채널이면 누가 더 잘 지시하는가" | "각자 최선을 다하면 무엇이 나오는가" |

두 레인의 결론을 섞어 한 문장으로 말하지 않는다.

**증거팩 = 스냅샷이다, JSON이 아니다.** JSON만 주는 건 우리 인코딩을 공유하는 것이지
경쟁 방법론의 입력을 공유하는 게 아니다(Impeccable은 래스터를, hallmark는 스크린샷/URL을
요구한다). 공유물은 **같은 날의 스냅샷 = 고정 URL + 원본 PNG + 측정 JSON**이고,
각 arm은 자기 계약이 읽는 층만 쓴다. 해석("figure-ground 실패 = 엣지투엣지" 같은)은
**우리가 넣지 않는다** — 넣으면 omd의 내부 언어를 상대에게 강제하는 것이다.

### T3-7 판정 축

UI만 보지 않는다. 사용자 요구대로 omd는 시스템까지 낸다 — 그럼 그 축도 채점 대상이다.

**공통 점수와 능력 커버리지를 섞지 않는다.** 한 arm만 내는 산출물을 공통 총점에
넣으면 채점표가 곧 우리 제품 사양서가 된다.

| 축 | 무엇을 본다 | 어디에 |
|---|---|---|
| 화면 결함 | 첫 렌더 결함 수 (정의를 문서에 명시할 것) | 공통 점수 |
| 근거 추종 | 생성물 vs 스냅샷 편차 | 공통 점수 |
| **브랜드 식별력** | 로고·카피 제거 후 블라인드 forced-choice | 공통 점수 |
| DESIGN.md | 브리프가 요구했을 때의 산출 품질 | 공통 점수 (형식 아닌 내용으로) |
| omd book / 상태 매트릭스 | 존재 여부와 유용성 | **능력 커버리지 — 별도 보고** |

**브랜드 식별력에는 천장 기준선이 필요하다.** 로고를 지운 *원본*을 사람이 구분하지
못하는 브랜드라면 생성물에 높은 식별력을 요구할 수 없다. 브랜드별 원본 인식률을
먼저 재고, 생성물 점수는 그 천장 대비로 읽는다.

**DESIGN.md 채점은 Core v2 고정 SHA 기준이다.** T1이 규격을 바꾸는 중에 T3가 그
규격 품질을 채점하면 결과가 나오는 즉시 구규격 결과가 된다.

## T1 — DESIGN.md 새 규격 (2순위)

### 문제 정의 (사용자 진술)

Google이 제안한 design.md 규격을 awesome-design-md 형태로 변용해 쓰고 있는데,
**모든 정보와 케이스를 담으려면 DESIGN.md가 감당 못 할 만큼 무거워진다**는 것이
440개를 쌓으면서 드러났다.

### 방향

아예 새로 만들지 않는다. **DESIGN.md가 담아야 할 정수는 유지**하고,
수집 정보로 구성하기 어려운 부분과 별도 파일·컴포넌트에서 처리할 부분을 **분리·위임**한다.

### 단계

| # | 단계 | 산출물 |
|---|---|---|
| T1-1 | 실측 — 440개의 실제 무게 분포 | 섹션별 바이트·결손률·중복률 통계 |
| T1-2 | 무엇이 정수인지 판정 | "이게 없으면 DESIGN.md가 아니다" 목록 |
| T1-3 | 위임 대상 분류 | 어느 정보를 어느 파일/구조로 뺄지 |
| T1-4 | **판정: v2로 충분한가** | 충분하면 v2 보강, 부족하면 새 규격 초안 |
| T1-5 | 왕복 테스트 | T1-4 판정에 따라 — 보강안 또는 새 규격으로 신규 1건 + 기존 3건 |
| T1-6 | 확정 | 규격 + 리더/라이터 계약 |

T1-1이 먼저인 이유: "무겁다"는 체감을 **수치**로 바꾸지 않으면 무엇을 뺄지 못 정한다.

**v3를 전제하지 않는다.** `spec/design-md-core-v2.md`가 이미 "본문은 계약, 상세는
그래프"라는 분리를 하고 있다. 산출물 이름을 v3로 미리 정하면 T1-1이 "v2로 충분한가"를
재기도 전에 재작성을 전제하게 된다. 그 판정은 T1-4에서 한다.

**문서화는 sol(medium)**, 규격 반박은 **grok-4.6**.
