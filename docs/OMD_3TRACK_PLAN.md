## T3 — 미디어 데이터셋 + 3자 비교 (1순위)

### T3의 진짜 질문

"이미지가 예쁜가"가 아니다. **"근거에서 유도했는가, 지어냈는가"** 다.
그래서 모든 산출물은 인용한 근거 필드를 달고 나온다.

### 이미 끝난 것

- grok imagine 접근·이미지·영상·다운로드 전 구간 실측 (README §7)
- 증거 캡처 도구 `test-v2/tools/capture-media-evidence.mjs`
- chrome / imagery 도메인 분리 — 광고를 브랜드 색으로 오인하던 결함 제거
- 무신사 1건 실측 완료

### 단계

| # | 단계 | 산출물 | 게이트 |
|---|---|---|---|

### T3-1 유도 규칙의 핵심

프롬프트는 자유 작문이 아니라 **템플릿 + 근거 슬롯**이다.

```
[매체] [종횡비=evidence.imagery.aggregate.aspects]
피사체: <새로 정의> — 프레임 내 위치 evidence.imagery.aggregate.subjectCenter
조명: evidence.imagery.aggregate.lightDirections 최빈값,
      다이내믹 레인지 evidence.imagery.aggregate.dynamicRange
톤: evidence.chrome.pageBackground 위에서 읽히도록
금지: 로고·워드마크·실제 제품명·타사 카피
```

슬롯이 비면 그 문장을 쓰지 않는다. 무신사처럼 figure-ground가 2/12로 미해결이면
subjectCenter 슬롯은 **비운 채로 나가고**, 대신 "엣지투엣지 크롭"이 근거가 된다.

### T3-6 비교의 공정 조건

세 arm 모두에게 **같은 것**을 준다.

| 주는 것 | 이유 |
|---|---|
| 동일 브리프 (브랜드·화면·목표) | 과제가 같아야 비교가 된다 |
| 동일 증거팩 (evidence.json) | 우리 도구로 만든 근거를 우리만 쓰면 조작이다 |
| 동일 생성 채널 (grok imagine) | 이미지 품질이 아니라 *지시 품질*을 본다 |

**다른 것은 방법론뿐이다.** 그게 측정 대상이다.

### T3-7 판정 축

UI만 보지 않는다. 사용자 요구대로 omd는 시스템까지 낸다 — 그럼 그 축도 채점 대상이다.

| 축 | 무엇을 본다 | omd 고유? |
|---|---|---|
| 화면 품질 | 첫 렌더 결함 수(G2 기준) | 아니오 |
| 근거 일치 | 생성물 vs evidence 편차 | 아니오 |
| DESIGN.md | 결정 ID ↔ 토큰 역참조, 희생 명시, 빈 값 처리 | **hallmark도 낸다 — 품질 비교** |
| 디자인 시스템 | 컴포넌트 상태 매트릭스, 해당 없음 사유 | 확인 필요 |
| omd book | 토큰 옆 근거, 대비 실측 vs 선언 대조 | 현재 omd 고유 |
| 재현성 | 같은 입력 → 같은 결과인가 | 확인 필요 |

## T1 — DESIGN.md 새 규격 (2순위)

### 문제 정의 (사용자 진술)

Google이 제안한 design.md 규격을 awesome-design-md 형태로 변용해 쓰고 있는데,
**모든 정보와 케이스를 담으려면 DESIGN.md가 감당 못 할 만큼 무거워진다**는 것이
440개를 쌓으면서 드러났다.

### 방향

아예 새로 만들지 않는다. **DESIGN.md가 담아야 할 정수는 유지**하고,
수집 정보로 구성하기 어려운 부분과 별도 파일·컴포넌트에서 처리할 부분을 **분리·위임**한다.

### 단계

| # | 단계 | 산출물 |
|---|---|---|
| T1-1 | 실측 — 440개의 실제 무게 분포 | 섹션별 바이트·결손률·중복률 통계 |
| T1-2 | 무엇이 정수인지 판정 | "이게 없으면 DESIGN.md가 아니다" 목록 |
| T1-3 | 위임 대상 분류 | 어느 정보를 어느 파일/구조로 뺄지 |
| T1-4 | 새 규격 초안 | `spec/design-md-core-v3.md` (가칭) |
| T1-5 | 왕복 테스트 | 신규 1건 + 기존 3건을 새 규격으로 |
| T1-6 | 확정 | 규격 + 리더/라이터 계약 |

T1-1이 먼저인 이유: "무겁다"는 체감을 **수치**로 바꾸지 않으면 무엇을 뺄지 못 정한다.
어느 섹션이 실제로 크고, 어느 섹션이 대부분 비어 있고, 어느 섹션이 파일 간 중복인지가
분리선을 결정한다.

**문서화는 sol(medium)**, 규격 반박은 **grok-4.6**.

## 공통 — 추적 (사용자 요구)

T3 요구사항: *"어떤 요청을 했고, 피드백 과정에서 어떤 내부 결과가 나왔는지 다 트래킹"*

`test-v2/03-runs/<run-id>/`에 run마다:

```
brief.md          무엇을 요청했나
prompt.txt        실제 보낸 프롬프트 원문
citations.json    각 문장이 인용한 evidence 필드 경로
grok.json         post UUID / conversation ID / 생성 파라미터
outputs/          결과 파일 + SHA
verify.json       대조 검증 수치 (구도·팔레트·휘도 편차)
feedback.md       무엇이 미달이었고 무엇을 바꿨나
```

재요청은 새 run이 아니라 같은 run의 이터레이션으로 append한다 — 왜 바뀌었는지가
남아야 의미가 있다.
