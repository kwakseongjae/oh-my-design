# 아프로디테 재시작 — 작품을 검증한 뒤 방법을 추출하기

상태: 제작/편입 제안. r10 결과물이나 새로운 사용자 점수는 아직 없다.

실행 모델·의존성·중단/완료 기준은 [통합 실행 계획](OMD_EXECUTION_PLAN_2026-09-07.md)의
A 트랙을 우선한다. Opus 5 제작, Grok 4.6 에셋, Sol 통합으로 나눈다.
아래 브리프는 A-0에서 확정할 후보이며, A-3 작품 채택과 A-6 스킬 출하는 별도다.

## 이번에 바꿀 판단

아프로디테의 상품은 **누군가 설치하고 싶어질 만큼 인상적인 한 페이지를 반복해서 만드는 능력**이다.
최초 플래그십 작품과 업종에 걸쳐 재현되는 하네스는 서로 다른 완료 조건이다.

기존 r2를 비교 기준으로 보존하되 디자인 언어를 영구 고정하지 않는다.
밝은 면·3D·영상에 대한 인과 판단은 보류한다. 효과 수·draw call 수·이미지 수·page height는
진단값이며 아름다움의 합격선으로 사용하지 않는다.

## r10의 구체적 제작 브리프

가상 제품 Higgsgen의 기존 약속은 장면·빛·재질을 통제하는 이미지 제작이다.
다음 페이지는 **“같은 장면을 내가 연출한다”를 방문자가 직접 경험**하게 한다.
이것은 새 창작 방향이며 아직 효과가 검증된 처방이 아니다.

한 공간, 한 피사체, 같은 카메라를 공유하는 이미지/영상으로 구성한다.
예를 들어 기존의 도자기 작업실을 유지한다면 작업실·작업물·창문·조명을 고정하고,
시간/빛/시점 변화만 만든다. 무관한 소금사막·포털·회랑으로 이동하는 장면은 제품 약속과
연결되는 이유가 있어야 한다. 61장을 모두 소화하는 것을 목표로 두지 않는다.

| 방문 순서 | 시각/동작 | 제품에서 전달하는 것 |
|---|---|---|
| 첫 화면 | 한 장면을 충분히 크게. 짧은 가치 제안과 작업 시작 CTA. 빛의 변화가 바로 보임 | 무엇을 제어하는 제품인지 이해 |
| 첫 전환 | 장면을 유지하며 빛/재질의 실제 차이가 드러남. 터치/키보드에서도 같은 선택 | 변화의 원인이 사용자의 선택임을 보여줌 |
| 증거 | 동일 subject/camera의 몇 개 결과를 비교. 선택하면 실제 프레임이 바뀜 | 연속성·제어 가능성을 눈으로 확인 |
| 작업 흐름 | 입력 → 선택 → 결과. 실제 데모가 처리하는 범위만 명시 | 제품의 사용 방식 |
| 마무리 | 결과를 가져가거나 작업을 시작하는 실제 연결 | 방문 이후 행동 |

표는 초기 가설이다. 필요한 섹션 수·페이지 길이를 기계적으로 맞추지 않는다.
먼저 **첫 화면과 첫 전환이 이어지는 작은 완성 구간**을 만든다. 그 구간에서 인상이
약하면 뒤에 여섯 섹션을 더 붙이지 않는다. 해당 구간을 r2와 같은 크기로 비교한다.

## 매체 선택

- **Grok Imagine**: 전체 페이지를 그리게 하기보다 hero still과 동일 장면 변형을 만든다.
  동일한 스타일 문구는 일관성을 보장하지 않으므로 실제 reference image/edit 경로를 확인하고
  subject·구도·재질이 유지되는지 결과를 보고 고른다. 실패한 컷도 trace에 남긴다.
- **영상**: 첫 전환의 빛/카메라 변화가 필요할 때 생성한다. 실제 출력 프레임으로 연결을
  검사한다. 각 클립을 좋은 프롬프트로 만들었다는 이유로 연속 장면이라고 가정하지 않는다.
- **Blender**: 물체·카메라·조명을 정확히 반복해야 할 때 한 scene을 만들고 여러 조명/시점으로
  렌더한다. 장식용 3D보다 재현 가능한 장면 제어가 사용하는 이유다.
- **Three.js**: 실시간 조작이 핵심 경험일 때만 사용한다. 이미지 평면을 터널에 걸고 카메라를
  움직이는 것만으로 통제 가능한 이미지 제품을 설명했다고 보지 않는다.
- **DOM/CSS**: 타이포·흐름·CTA·상태를 담당한다. 그레인·글래스·메시는 작품에 필요할 때 선택한다.

현재 머신에 Blender, ffmpeg, Grok 실행 파일이 있다. 이는 생성 채널이 성공한다는 증거가 아니다.
생성 전 작은 probe로 출력·참조 지원·비용 기록·다운로드를 확인한다.

미리 만든 프레임 선택 데모를 실제 AI 생성 기능처럼 표현하지 않는다.
라이브 서비스가 없는 가상 제품의 CTA는 실제로 동작하는 샘플 다운로드/선택 데모 등에 연결하고
비공식 컨셉임을 표시한다.

## 평가 계약

**기능 바닥**: overflow·잘림·텍스트/포커스 대비·핵심 CTA·모바일·키보드·reduced-motion·
실제 네트워크/에셋 로드·영상 seek·페이지 무게를 확인한다. 검사 불능은 미검증이다.

**편집 검토**: 카피의 명사/동사가 화면의 subject와 맞는지, 장면 변형이 실제로 같은 대상인지,
헤드라인이 내부 작업 지시를 복사한 것은 아닌지, 본문이 제품 약속을 증명하는지 본다.
manifest의 subject/caption mapping은 검토를 돕는다. 문자열 린트를 의미 검증으로 대체하지 않는다.

**미적 판단**: 동일한 환경에서 r2·후보·해당 목적의 기준 화면을 익명 비교한다.
평가 전에 검사 점수·에이전트 평가·사용 기술을 보여주지 않는다. 사람의 선택과 이유를 기록한다.
오너의 작품 승인과 여러 사람의 선호는 각각 기록한다. 합성 페르소나를 수요 검증으로 쓰지 않는다.

## 스킬에 포함시키는 순서

1. 한 작품을 완성하고 실제 페이지와 짧은 시연 영상을 오너가 평가한다.
2. 무엇이 효과적이었는지 source/asset/interaction 수준의 결정을 추출한다.
3. 아프로디테 계약을 짧은 작업 흐름으로 재작성한다:
   제품 약속 → visual direction → asset proof → 작은 완성 구간 → 전체 페이지 → 기능/편집/선호 검토.
4. LI 검사 중 접근성/파손 항목은 hard gate로, 스타일/개수 항목은 설명적 진단으로 분리한다.
   어떤 항목을 강등할지는 정확한 rule별로 분류해 기록한다. 실패 출력 전체를 무시하지 않는다.
5. 독립적인 다른 업종 두 개에서 같은 스킬을 실행한다. Higgsgen의 색·사진·구도가
   그대로 복제되면 일반화된 하네스라고 주장하지 않는다.
6. npm 설치본에서 font/media/check dependencies와 경로가 닫히는지 테스트하고,
   aphrodite fixture를 release matrix에 넣는다. canonical/mirror/doctor/docs를 함께 검증한다.
7. 초기에는 명시적 aphrodite 호출로 제공한다. 자연어 자동 라우팅은 `workflow-capabilities.json`과
   `workflows.ts`에 추가하고 router 테스트로 일반 UI 작업이 무거운 제작 경로에 빠지지 않게 한다.

**출시할 수 있는 표현**: 한 작품이 통과하면 “Aphrodite preview + 제작 소스/영상”.
다른 업종과 설치본까지 검증되면 정식 제작 경로. 한 작품의 수작업 성공을 스킬 일반 성능으로
바로 확대하지 않는다.
