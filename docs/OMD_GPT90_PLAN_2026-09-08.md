## 시간 운영

- 0–25분: 최초 실행본과 실패 재현을 확보한다. 문서만 쌓지 않고 실제 화면·프로세스·파일 변화를 확인한다.
- 25–60분: 최초 결과를 root가 인수하고 결함을 수정한다. 먼저 끝난 워커를 패키징/콘텐츠 독립 검토에 재배치한다.
- 60–80분: 주요 변경의 통합 검사, 실제 화면/영상, 명령 예제 실행, 콘텐츠 라우트 준비를 마친다.
- 80–90분: 새로운 큰 변경을 줄이고 결과 SHA, 테스트 결과, 남은 관문, 다음 순서를 기록한다. 시간 종료 전 진행 중인 자체 프로세스를 정리한다.

공유 파일 수정은 root가 직렬화한다. Chrome Computer Use는 root만 사용하며 외부 서비스 작업도 이 슬롯을 따른다. 격리된 로컬 Chromium 테스트는 사용자 Chrome 상태를 공유하지 않는다. Blender는 실제 결과의 품질을 올리는 경우 투입하며, 도구 사용 자체를 목표로 삼지 않는다.

## 이 작업 이후의 권장 순서

1. **Core 4 canary와 설치본 신뢰성**: 스테이징 리허설을 인수한 뒤 정확한 정본 채택 패키지를 검토한다. 손실·오귀속이 하나라도 있으면 해당 배치를 중지한다. 통과 후 후속 10개로 넓힌다.
2. **ODDLY 실제 화면 채택**: 캐릭터 인상과 첫 펼침/세계 진입을 오너가 판단한다. 채택한 제작 과정에서 재현 절차를 추출한다. 색상이나 효과 개수를 모든 랜딩의 규칙으로 일반화하지 않는다.
3. **벤치 calibration**: 4조건의 같은 모델·시간·도구 권한을 고정하고 각 조건이 에셋을 직접 만든다. 순정 조건은 스킬·전역 훅·다른 결과를 받지 않는 실행 환경이어야 한다. 이번 native 협업 에이전트의 결과를 순정 비교에 재사용하지 않는다.
4. **작은 발행 묶음**: 배민 글과 Core 실전 글을 실제 ko/en 라우트에서 검토한다. Home→Builder→handoff 측정이 배포된 시점 이후 14개 완료일을 관찰한다. 글 공개와 성과 판정을 한 날짜의 완료 작업으로 합치지 않는다.
5. **스킬 전이와 본 실험**: Aphrodite는 새 업종 2개×2회에서 재현성과 차별성을 검사한다. 벤치는 calibration4 + 초기36 + 후속12 셀을 수행하고 전체 실패 분모를 공개한다. 에셋 평가를 먼저 동결하고 페이지 평가를 진행한다.
6. **출시와 바이럴 묶음**: 실제 동작 영상, 조건·버전·에셋 이력, 전체 결과 링크를 함께 준비한다. 우승이 없어도 실패 유형과 개선 과정을 콘텐츠로 사용한다. 미적 선호를 합성 점수로 대체하지 않는다.

## 모델 배치 판단

- Astra: 장면 설계·복잡한 3D 구현·표준 경계와 제품 판단·최종 인수. 시각 판단은 실제 렌더와 사용자 피드백을 따른다.
- Sol: 소비 코드·스키마/이관·프로세스 제어·검사/패키징·회귀 수정. 파일 소유권이 분리되면 병렬 실행한다.
- Grok/Opus: 이번 90분에는 호출하지 않는다. 추후 비교 모델로 선택하면 새 epoch에서 모델과 권한을 동결한다. 이전 결과와 섞어 모델 효과를 주장하지 않는다.
- Fable: 필요성이 확인되지 않아 투입하지 않는다.

## 사용자에게 보여줄 관문

실행 선택은 재질문하지 않는다. ODDLY의 실제 화면/모션과 원본 시안 차이, 기업 창작 예제의 시각 방향, 실제 게시·출시 패키지처럼 사용자의 판단이 필요한 결과를 준비한 다음 검토를 요청한다. 로컬 회귀 PASS를 이 관문들의 승인으로 간주하지 않는다.
