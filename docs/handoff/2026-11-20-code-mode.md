## 4. 차례대로 할 일

**차례 1 — 로드맵 고쳐 쓰기와 브리핑(본 세션, 비용 없음).** 방향이 바뀌었으니 `docs/ROADMAP.md`부터 고친다.

- T2의 「일본어 → 대만 → 중국, 하나씩」을 「일본어는 글쓰기 규칙, 대만·중국은 설계와 조사를 같이」로.
- T3(앱 중심 회사)를 「서비스 단위 화면 아카이브: 모바일 / 웹 / 둘 다」로 다시 정의.
- T6(3D·셰이더)에 시각 효과 스킬을 넣는다.
- 새 트랙 또는 T0에: 우리 사이트의 디자인 시스템과 `/design.md`.
- 「레퍼런스와 업데이트가 핵심」(오너)을 맨 위의 방향 문장에 반영한다. 아래 「화면 아카이브 설계안」의 「업데이트」 절이 재료다.
- 고친 뒤 오너에게 스프린트 목표, 단일·다중 트랙 여부, 레인별 첫 산출물을 짧게 브리핑하고 바로 다음 차례로 간다(오너가 「작업 들어가자」고 했다).

**차례 2 — 화면 아카이브를 웹까지(본 세션 + 빌더 에이전트 1).** 아래 설계안은 앞 세션의 제안이다. 오너가 정한 것이 아니다.

- 단위는 앱이 아니라 **서비스**다. 서비스마다 `platform: mobile | web | both`를 붙인다.
  - 모바일만: 핵심 경로가 앱에만 있다(토스. 웹은 소개 사이트다).
  - 웹만: 제품이 브라우저에서 쓰인다(B2B SaaS, 채용·문서 도구).
  - 둘 다: 웹과 앱이 같은 일을 하고 화면 문법이 비슷하다(오늘의집, 무신사, 29CM). 같은 화면 유형을 나란히 놓는 것이 이 묶음의 값이다.
  - 가르는 물음 하나: 「이 서비스의 핵심 경로(`tools/phone-recorder/apps.json`의 `core_route`)를 웹에서 끝까지 갈 수 있는가」.
- 웹은 폰이 없어도 된다. 레퍼런스 수집에 쓰는 창 없는 캡처(`scripts/workers/spawn.sh --mcp capture-headless`, `web/scripts/compile-evidence.mjs`가 읽는 캡처)를 화면 단위로 쓴다. 폭은 1440과 390.
  로그인 뒤 화면은 시범 계정이 필요하다(계정은 오너가 만든다). 봇 차단(Cloudflare 등)은 우회하지 않는다. 막히면 그 서비스는 「웹 불가」로 적는다.
- 화면 유형과 흐름의 이름은 모바일과 같은 것을 쓴다(`tools/phone-recorder/taxonomy.json`). 웹에만 있는 유형(가격표, 문서, 대시보드)은 추가한다.
- **우리만의 값: 화면 ↔ 잰 토큰.** 열 개 앱 모두 카탈로그에 DESIGN.md가 있다. 화면의 버튼·카드를 그 서비스의 토큰 이름으로 잇는다. Mobbin·Refero에 없는 것이다.
- **업데이트.** 웹은 같은 경로를 주기적으로 다시 찍어 바뀐 화면만 올린다(자동). 모바일은 `phone.mjs replay`로 같은 경로를 다시 찍는다.
  사이트에는 「이번 주에 추가·변경된 것」이 한곳에 보여야 한다(피드, RSS, MCP 도구). 레퍼런스의 재측정(`scripts/t1/remeasure.mjs`)도 같은 피드에 싣는다.
