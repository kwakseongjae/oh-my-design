## Scope and collector boundary

- Local Playwright-driven Chrome (Tier 1), 1440×1000, `ja-JP` with a matching
  `accept-language`, light scheme forced, `getComputedStyle` on the document element and on
  individual controls, clicks suppressed in the capture phase.
- Logged out. No account was created and no sign-in was attempted.
- Desktop, **light mode only**. A theme toggle exists in the header and was not pressed.

### Two collectors, on purpose

The token dump and the first state pass were run by a **delegated subagent** (Sonnet) as part
of the collection-model trial recorded in `docs/COLLECTOR_MODEL_TRIAL_2026-09-22.md`. Its
headline claim — that the buttons carry **no** authored focus ring — was then **independently
re-measured** before being written here, because a claim of that shape is exactly the kind
this catalog has been wrong about before.

The re-measurement confirmed it and **strengthened it**; see below. Both runs are cited.

## Namespace ownership

**All 129 custom properties are Zenn's.** No framework prefix appears at the document element
— no `--tw-`, `--wp-`, `--el-`, `--mantine-`, and no `oklch` shadcn layer.

Namespaces: `--c-*` 109 · `--rounded-*` 8 · `--spacing-*` 8 · `--font-*` 3 · `--header-*` 1.

**A note on method.** Reading `document.styleSheets[].cssRules` returns nothing here: all
twelve of Zenn's CSS chunks are served from `static.zenn.studio`, which Chrome treats as
cross-origin for rule access. `getComputedStyle` on the document element resolves regardless
of stylesheet origin and is what was used. Worth recording because a stylesheet-text approach
would have reported "no tokens" on a site that has 129.

No nonsense-path control was run on this host. The reference cites **one route only**, so no
sub-route is being relied on; this is noted in the limitations rather than claimed as a pass.

### The focus finding, and the check that settled it

Every measured button computes `outline-style: none` at rest and under focus. The primary
variant adds nothing in its place, so **focus renders identically to hover** — same fill, no
ring, no shadow.

"No ring" has an innocent reading — that the browser's default was never there — and a
serious one. The two were separated by **pressing a real Tab key**: focus landed on Zenn's
logo link, which computes `outline: rgb(0, 95, 204) auto 1px`. That is Chrome's default
(`docs/MEASUREMENT_METHOD_2026-09-22.md` §2.5), **alive on this page**.

So the default is available and the button component suppresses it. The secondary variant
replaces it with an authored box-shadow; the primary does not replace it at all. Recorded as
measured, in §4 and §13 of the reference, without an accessibility verdict attached — the
observation is the deliverable.

### What the delegation got right, and what was checked anyway

The subagent hit and worked around a trap in this repo's own tool: an untargeted `#fff` match
with `--text` picked up `<body>`, because the text needle substring-matches ancestors. It
pinned with `--height 40` instead. It also reported the `forcus` typo, the `-rgb` triplet, and
the Inter scoping.

Everything above was re-measured before being written. The one thing the delegated run could
not do was the Tab-key check, which is what turned "no ring" from a reading into a finding.
