### Correction — the focus ring was the browser's, and I recorded it as DeepSeek's

Originally written up here as "the first confirmed focus ring after the method correction":
focus was read before the mouse touched the control, `:focus-visible` matched true, and a
`#005fcc` outline rendered. All of that is accurate. **The conclusion drawn from it was not.**

Re-measured on 2026-09-22 with a control the first pass never ran: a page set with
`setContent` and **no author stylesheet at all**. Chrome paints
`outline: rgb(0, 95, 204) auto 1px` on a bare `<button>`, `<a>` and `<input>`, in both light
and dark schemes. That is byte-for-byte what DeepSeek's pill returned.

`#005fcc` is Chrome's default `:focus-visible` ring. The tell is in the value itself — the
style is **`auto`**, which no author writes; an authored ring names a style and a width. The
focus token has been removed from `button-secondary`, and §4 and §14 now say what actually
renders and whose it is.

This is the same class of error the catalog already refuses elsewhere — cybozu's `#2693ff`
focus ring and ctrip's `#0000ee` / `#ff0000` link colours were excluded as browser defaults.
It reached the token layer here because a *positive* focus observation, after a session spent
fixing *negative* ones, read as the fix working rather than as a value needing a control.

### Fonts — and a correction made 2026-09-22

`tokens.typography.family` **is** set here, unlike every other CN reference measured. But it
records **one** face, not two.

Re-audited against `document.fonts` after the method note in
`docs/MEASUREMENT_METHOD_2026-09-22.md` §2.6 was written. The page declares six `@font-face`
entries:

```
DM Sans     400  loaded      Montserrat  400  loaded
DM Sans     500  loaded      Montserrat  500  unloaded
DM Sans     700  unloaded    Montserrat  600  unloaded
```

**`Fragment Mono` is not among them.** It is named in `--ds-font-mono`
(`"Fragment Mono","Roboto Mono",ui-monospace,monospace`) and falls through. The first pass
recorded it as a brand face on the strength of the token name alone; that was wrong and
`tokens.typography.family.mono` has been removed. It is described in §3 instead.

`Montserrat` loads at 400 and appears in **no** `--ds-font-*` token, so it is not recorded
either — a loaded face with no token is as unclaimable as a token with no loaded face.

## Tier 2 cross-checks

getdesign.md and refero.design return no DeepSeek record — the ordinary CN outcome, and why
the regional rule requires two brand-owned sources. Both cited sources are DeepSeek-owned.

## Evidence limitations

- **Two controls.** The chat app (`chat.deepseek.com`) and the API platform were not measured.
- The primary and ghost button variants are declared and were **not observed rendering**;
  their values are recorded as tokens, not as component states.
- Surfaces are translucent (`hsla`/`rgba`) and are recorded as authored. Flattening them to
  hex would lose the glass the design depends on.
- No motion or transition token exists among the 82. Desktop only.
