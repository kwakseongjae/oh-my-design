## 1. 비교 단위와 두 레인의 경계

비교 단위는 `레인 × 브랜드 × arm × 반복`이다. 브랜드는 계획에 확정된 9개이며,
각 브랜드·arm·레인을 **4회** 독립 실행한다. 따라서 레인 하나의 arm당 36 run,
세 arm 합계 108 run이다. 무신사 T3-3 파일럿은 교정에만 쓰고 이 36회에 포함하지 않는다.

모든 run은 같은 브랜드 스냅샷(고정 URL, 원본 PNG, 측정 JSON, manifest SHA), 같은 화면
브리프, 같은 필수 산출물 목록을 받는다. **공통 브리프에는 지정 화면의 과업, 공통 필수
산출물, 스냅샷 handle(`snapshot_id`, PNG SHA, `verify.json` block ID)만 넣는다.** T3-1의
슬롯 문장, evidence 필드 해석, 구도·브랜드·이미지 역할에 관한 우리 측 해석은 넣지 않는다.
화면별 과업과 핵심 콘텐츠는 §4.1 코드북에서 별도로 잠근다. arm 순서는 실행 전에
`SHA-256("<lane>|<brand>|<repeat>|T3")`의 첫 바이트를 6개 순열에 매핑해 정한다.
팩 SHA, 모델·버전, 브리프 SHA, 스냅샷 SHA, 순서, 시작·종료 시각을 run manifest에 남긴다.

| 구분 | 레인 A — Controlled | 레인 B — Native |
|---|---|---|
| 질문 | 같은 근거·같은 생성 채널에서 누가 더 잘 지시하는가 | 각 팩의 본래 워크플로가 무엇을 완성하는가 |
| 입력 | 동일 브리프 + 동일 스냅샷 | 동일 브리프 + 동일 스냅샷 |
| 생성 경로 | Grok Imagine 고정 | 각 팩의 고정 SHA가 정한 네이티브 경로 |
| 허용 주장 | **지시 품질** | **스킬 전체 능력** |
| 집계 | 레인 A 안에서만 순위·통과 판정 | 레인 B 안에서만 순위·통과 판정 |

레인 A와 B의 점수를 합산하거나 평균내지 않는다. 한 레인의 우승을 다른 레인의 우승처럼
서술하지 않으며, “종합 우승”도 만들지 않는다.

## 2. 공통 필수 산출물과 능력 커버리지

각 run의 공통 필수 산출물은 (1) 지정 화면의 실행 가능한 첫 렌더, (2) 그 화면에 쓰는
대표 생성 이미지, (3) **형식 자유인 디자인 시스템 설명 문서**다. 세 arm 모두 브리프에서
이 문서를 명시적으로 요청받는다. 파일명이 `DESIGN.md`인지, Core v2 절 순서를 따르는지,
결정 ID가 있는지는 채점하지 않는다. HTML 주석, README, native `design.md`, 추출 문서도
같은 내용 기준으로 읽는다.

다음은 공통 총점에서 **명시적으로 제외**하고 별도 능력 커버리지 표에만 `제공 / 미제공`,
실행 가능 여부, 0–4 유용성 평정과 근거를 기록한다.

- omd book 또는 이에 대응하는 별도 탐색기
- 컴포넌트 상태 매트릭스
- arm 고유 검사기·리포트·추가 화면
- **시맨틱 아트디렉션 주석 계층**

시맨틱 아트디렉션은 실행 화면·대표 이미지·디자인 시스템 문서와 분리된 별도 주석 계층
산출물이다. 이번 루브릭의 공통 브리프·공통 총점에서 **제외**한다. pack이 내부 추론에
쓰는 것은 막지 않지만, 주석 계층을 산출했거나 그 계층에서 이미지 역할을 선언했다는
이유로 §4.2를 포함한 어떤 공통 축에도 점수를 주지 않는다.
능력 커버리지는 순위·통과·우승 문장에 사용할 수 없다.

## 3. 평가자와 블라인드

- 독립 평가자 **5명**이 모든 인간 판정 항목을 채점한다. 결원 교체용 평가자 2명을 실행
  전에 등록하되, 교체자는 해당 배치 전체를 처음부터 채점한다. 한 항목을 4명 이하의
  점수로 집계하지 않는다.
- 평가자는 세 arm의 구현자가 아니어야 하고, arm 코드·파일명·로그·실행 순서를 보지
  않는다. 산출물은 레인별 난수 ID로 익명화한다. 디자인 시스템 원문은 평가자에게 직접
  공개하지 않고 아래 중립 전사본만 채점한다.
- 평가에 참여하지 않는 전사 담당자가 원문의 문장·수치·예시를 내용 손실 없이 옮긴다.
  제목 계층만 중립화하고 원문의 절·문장 순서를 보존하며, 내용을 재분류·요약·보강·평가하지
  않는다. 허용 변환은 표지 삭제와 경로 삭제뿐이다. 원문 SHA와 전사본 SHA 및 문장 대응표를
  봉인한다.
- `evidence.*` 필드나 decision ID가 존재했다는 사실은 점수를 올리지 않는다. 제거된 표지
  아래의 실제 문장만 해당 내용 항목의 앵커를 만족할 때 점수에 들어간다.
- 레인 A와 레인 B는 평가자별로 **서로 다른 채점 세션**에서 채점한다. 두 레인의 난수
  순서는 서로 다른 salt로 만든다. 두 전체 순서가 같으면 B salt에 1을 더해 달라질 때까지
  다시 만들며, 같은 브랜드의 A/B 산출물을 나란히 또는 연속 비교할 수 있는 화면을
  제공하지 않는다. 평가자 절반은 A→B, 나머지는 B→A로 순서를 교차 배정하며, 두 세션
  사이에는 다른 레인의 점수·산출물·정답을 공개하지 않는다.
- 5명은 T3-3 파일럿으로 결함 severity와 0–4 내용 앵커를 교정한다. 파일럿 점수와 토론
  내용은 본 실험에 들어가지 않는다. 파일럿 앵커도 본 실험과 같은 패킷 형식으로만
  교정한다. 본 실험에서는 서로 상의하지 않는다.

모든 채점을 제출한 직후, 정답 공개 전 각 평가자는 각 레인의 각 익명 산출물마다 arm을
3지선다로 한 번만 추측하고 근거를 `형식 단서 / 내용 단서 / 시각 단서 / 추측` 중 하나로 표시한다. 원시
블라인드 파손률은 `B_raw = 정답 추측 수 / 전체 추측 수`, 우연 보정 파손률은
`B_adj = max(0, (B_raw - 1/3) / (1 - 1/3))`로 계산하고 Wilson 95% CI와 함께 레인별로
보고한다. 이 값은 점수 가산에 쓰지 않는다. `형식 단서`로 표시된 추측만 모은 부분집합의
`B_raw` 95% CI 하한이 `1/3`보다 클 때만 해당 레인의 블라인드를 `COMPROMISED`로 표시하고
단독 우승을 선언하지 않는다.

평가자 간 일치도는 레인별·인간 판정 축별로 계산한다.

| 판정 | 측정 | 최소 기준 |
|---|---|---|
| 결함 존재 여부 | Krippendorff's alpha, nominal | `alpha >= 0.67` |
| 결함 severity와 0–4 내용 평정 | Krippendorff's alpha, ordinal | `alpha >= 0.80` |
| 브랜드 9지선다 | Krippendorff's alpha, nominal | `alpha >= 0.67` |

최소 기준에 못 미치면 결과를 공개하거나 순위를 내지 않는다. 파일럿 앵커를 한 번만
수정하고 해당 레인·축의 **전 항목을 새 익명 순서로 재채점**한다. 두 번째도 미달이면
그 레인 전체는 `INCONCLUSIVE — rater agreement failed`이며, 낮은 일치도를 다수결로
덮지 않는다.

## 4. 공통 점수와 축별 가중치

각 축은 0–100점이다. 5명 인간 평정은 먼저 평가자 평균을 낸다. run 점수 → 브랜드별
4회 평균 → 브랜드 동일가중 macro-average 순서로 집계하며, `N/A-ceiling`의 정확한 분모와
총점 재정규화는 §4.5 식을 쓴다. 이미지가 많은 브랜드가 더 큰 가중치를 갖지 않는다.
첫 렌더 결함 축만 §4.1의 첫 캡처를 쓰고, 나머지 세 축은 허용된 자기검수·수정까지 끝난
최종 산출물을 쓴다.

| 공통 축 | 레인 A | 레인 B | 판정 주체 |
|---|---:|---:|---|
| 첫 렌더 결함 | 20% | 30% | 블라인드 인간 판정 |
| 근거 추종 | 40% | 20% | `verify.json` 70% + 인간 의미 판정 30% |
| 브랜드 식별력(원본 천장 보정) | 25% | 25% | 블라인드 인간 9지선다 |
| 디자인 시스템 문서 내용 품질 | 15% | 25% | 블라인드 인간 판정 |
| 합계 | **100%** | **100%** | 레인별 독립 |

### 4.1 첫 렌더 결함의 정의

이 문서에서 **첫 렌더**는 평가 harness가 지정 route에서 최초 HTTP 2xx와 비어 있지 않은
`main`을 감지한 즉시, 다음 arm completion이나 수정 tool call을 허용하기 전에
`1440×1000`과 `390×844`로 캡처한 기본 상태다. 평가자 피드백·스크린샷 비평·사람의
수동 수정은 당연히 그 뒤다. 최초 성공 load 전의 컴파일 오류 수정은 허용한다. arm이
최초 load 뒤 스스로 화면을 보고 고친 경우에도 수정 전 캡처가 첫 렌더다. 이 정의는 레포
다른 문서의 `G2`와 무관하다.

  대표 이미지 부재가 이 화면의 사실이므로, `H1` 관련 결함은 이 브랜드에 적용하지 않는다.

- 핵심 과업: 필터를 적용해 채용 카드 하나를 연다.
- `K1` 상단 내비 (0, 0, 1, 0.06)
- `K2` 필터 바 (0, 0.08, 1, 0.16)

- 폴드 아래 허용: 추가 카드 행

| 잠금 필드 | 허용 값 |
|---|---|
| 핵심 과업 | 화면에서 사용자가 끝내야 하는 단일 관찰 가능 행동 한 문장 |
| 핵심 콘텐츠 | `K1..Kn` region ID, viewport별 캡처 내 기준 사각형, 필수 텍스트·컨트롤 |
| 대표 이미지 | `H1` region ID와 그 이미지가 화면에서 수행해야 하는 역할 한 문장 |
| 허용 폴드 아래 콘텐츠 | 최초 캡처 아래에 정상적으로 이어져도 되는 region ID |

평가자는 DOM이나 소스 코드를 보지 않고, 두 첫 캡처 위에만 결함을 표시한다. 결함 제보의
식별자는 `(viewport, region ID, defect code, 보이는 증상)`이다. `region ID`는 잠금표의
`K*`·`H1` 또는 고정 격자 `G[row,column]`를 쓴다. 다음 조건을 모두 만족할 때만 여러 제보를
한 결함으로 합친다: defect code가 같고, region ID가 같고, 보이는 증상이 같은 시각적
연속체다. 두 viewport의 제보도 이 규칙을 만족하면 하나로 합쳐 더 높은 severity를 쓰고,
하나라도 다르면 별도 결함이다. 구현 원인이나 요소 동일성을 추정해 합치지 않는다.

고정 defect code는 `LOAD`(빈 화면·crash), `TASK`(잠긴 핵심 과업 불가), `CLIP`(캡처
사각형 **안에서** 필수 픽셀·문자·컨트롤이 경계나 다른 요소에 의해 잘림), `OVERLAP`,
`H-OVERFLOW`, `STATE`, `CONTRAST`, `FOCUS`, `KEYBOARD`, `HERO`, `BRAND-MARK`, `LOCAL`이다.
정상적으로 캡처 아래로 이어지는 문서 흐름과 잠금표의 허용 폴드 아래 콘텐츠는 `CLIP`이
아니다. `CONTRAST`는 캡처 색상 샘플로 WCAG 2.x contrast ratio를 계산해 일반 텍스트
`<4.5:1`, 큰 텍스트·필수 UI 경계·아이콘 `<3:1`일 때만 성립하며 측정 좌표·전경·배경
RGB와 계산값을 기록한다. **대표 이미지 실패는 `H1`이 누락·깨짐·완전 공백이거나, 크롭·
가림 때문에 5명 중 3명 이상이 잠금표의 필수 주 피사체·정보를 식별하지 못한 경우다.**

5명 중 3명 이상이 위 식별자로 존재한다고 한 결함만 센다. severity는 다수결, 동률이면
더 높은 severity다.

- `P0`: `LOAD`, 잠긴 `TASK` 완료 불가, `K*` 핵심 콘텐츠의 `CLIP`, 로고·워드마크 금지
  위반, 키보드만으로 잠긴 핵심 과업 불가.
- `P1`: 핵심 과업은 가능하지만 주요 `OVERLAP`·`H-OVERFLOW`, 잘못된 `STATE`, 수치로
  확인된 `CONTRAST`, `FOCUS`, `HERO`가 있다.
- `P2`: 과업과 정보 이해를 막지 않는 국소 정렬·간격·크롭·타이포·장식 결함이다.

점수는 `max(0, 100 - 40×P0 - 10×P1 - 3×P2)`다. 디자인 취향 차이, 브리프에 없는
추가 화면의 결함, 네트워크가 끊긴 외부 링크는 세지 않는다.

### 4.2 근거 추종

`verify.json`은 T3-0/T3-1을 통과해 **eligible**로 표시된 evidence 필드만 읽는다.
결측 필드를 추정하거나 인접 필드로 대체하지 않는다. 수치 점수는 아래 필드별 점수의
산술평균이다. `clamp(x)`는 0–100 범위 절삭이다.

| 필드 | 오차 `e` | 필드 점수 |
|---|---|---|
| 종횡비 | `abs(gen/source) - 1` | `clamp(100 × (1 - e/0.10))` |
| 평균 휘도 | 0–1 절대차 | `clamp(100 × (1 - e/0.20))` |
| 다이내믹 레인지 | 0–1 절대차 | `clamp(100 × (1 - e/0.20))` |
| 피사체 중심 | 정규화 좌표의 Euclidean 거리 | `clamp(100 × (1 - e/0.25))` |
| 팔레트 | 아래 고정 팔레트 절차의 coverage 가중 평균 `ΔE00` | `clamp(100 × (1 - e/25))` |

팔레트 절차는 `test-v2/tools/analysis.mjs`의 실제 측정과 동일하게 고정한다. source와
generated 이미지를 각각 sRGB의 채널별 **5-bit**(`channel >> 3`, 총 `32^3` bin)로
양자화하고, 픽셀 수 내림차순 상위 `k=6` bin을 쓴다. 각 bin 색은 그 bin 소속 원본 8-bit
RGB 픽셀의 채널별 산술평균이고, coverage는 `bin pixel count / frame pixel count`다.
source 상위 bin `i`마다 generated 상위 6 bin 중 CIEDE2000 `ΔE00`가 최소인 값을 `d_i`로
잡으며 일대일 매칭은 강제하지 않는다. 팔레트 오차는
`e_palette = Σ_i(coverage_i × d_i) / Σ_i coverage_i`다. RGB→Lab은 D65, sRGB 표준 전달
함수를 사용한다. `analysis.mjs`가 coverage를 소수 넷째 자리로 저장하므로 점수 계산도
그 저장값을 사용한다.

팔레트·휘도·다이내믹 레인지는 그날 스냅샷 추종 지표일 뿐 브랜드 불변량이나 브랜드
식별력으로 해석하지 않는다. eligible 수치 필드가 2개 미만이면 그 스냅샷은 비교 입력
불충분으로 보고 세 arm의 해당 block을 실행 전에 교체한다.

인간 의미 판정 30%는 **스냅샷 충실도만** 본다. 별도 시맨틱 아트디렉션 주석, pack이
선언한 이미지 역할, 브랜드 사실의 양, T3-1 슬롯 해석은 보지 않는다. 수치 지표가 직접
재지 않는 관찰 가능한 전경/배경 관계, 요소의 상대적 크기·겹침·반복, 시각적 위계와
크롭의 전체 인상이 스냅샷과 얼마나 일치하는지를 `0=관찰 가능한 관계가 거의 반대`,
`1=대부분 불일치`, `2=혼합`, `3=대부분 일치`, `4=핵심 관계와 전체 인상이 일치`로
평정해 25를 곱한다.
축 점수는 `0.70 × verify 수치점수 + 0.30 × 인간 의미점수`다.

**충돌 규칙:** 측정 가능한 필드에서는 `verify.json`이 승자이며 인간이 숫자를 덮어쓰지
않는다. 비수치 스냅샷 관계·시각 위계에서는 인간 판정이 승자이며 verify가 이를
대체하지 않는다. 둘이 반대여도 위 70:30 식을 그대로 적용하고 사후 재량 조정은 없다.
verify 도구 오류가 세 arm에 공통이면 해당 block 전체를 보류·수리 후 재실행한다. 한 arm의
잘못된 파일 때문에 verify가 못 읽으면 그 arm의 verify 부분은 0점이다.

### 4.3 브랜드 식별력과 원본 천장

생성물 공개 전에 같은 5명이 브랜드명·로고·워드마크·고유 카피를 중성 패치로 지운
원본 자극을 보고 9개 브랜드 중 하나를 강제로 고른다. 브랜드별 원본 4개를 사용하며
마스크 좌표와 이미지 SHA를 보존한다. `C_b`는 브랜드 `b` 원본의 정답률, 우연 확률
`q`는 `1/9`다.

원본 천장은 run과 분리한다. 평가자 `j`, 원본 자극 `s`의 정답을 `c_{b,s,j}∈{0,1}`라 할 때
`C_b = (1/(4×5)) Σ_s Σ_j c_{b,s,j}`다. `C_b`는 브랜드당 한 번만 계산해 봉인하는 보정
상수이며 4회 반복 관측치로 복사하거나 bootstrap의 반복 표본으로 취급하지 않는다.

생성물도 같은 방식의 9지선다로 채점한다. arm `a`의 개별 run `r`에 대해 평가자 `j`의
정답을 `x_{b,a,r,j}∈{0,1}`라 하고, run별 식별률을
`g_{b,a,r} = (1/5) Σ_j x_{b,a,r,j}`로 둔다. run별 식별력 점수는
`I_{b,a,r} = 100 × min(1, max(0, (g_{b,a,r} - q) / (C_b - q)))`다. 브랜드 식별력 점수는
네 `I_{b,a,r}`의 평균이며 `G_b` 같은 브랜드 단위 값을 네 run에 복제하지 않는다.

단, `C_b <= q + 0.10`이면 원본조차 신뢰성 있게 구분되지 않는 브랜드이므로 그 브랜드의
네 run 모두 식별력 축은 `N/A-ceiling`이다. 원본 천장이 낮다는 이유로 생성물에 원본보다
높은 식별력을 요구하지 않으며, 100점을 넘겨 보상하지 않는다. 총점·축 macro-average와
PASS 입력의 정확한 처리는 §4.5를 따른다.

### 4.4 디자인 시스템 문서의 **내용** 품질

`spec/design-md-core-v2.md`의 고정 SHA-256
`f8cd0ddfb1696a59c431ee1d459964ba925ead29275f9a448444caff9c93a1a4`는 용어 해석 참고본일
뿐 형식 체크리스트가 아니며 채점·전사 패킷에는 첨부하지 않는다. 아래 다섯 항목을 각각
0–4로 평정해 가중합 후 25를 곱한다.

| 내용 항목 | 축 내부 가중치 |
|---|---:|
| 스냅샷 또는 pack이 밝힌 방법에서 읽히는 입력이 화면 결정으로 이어지는가 | 25% |
| 색·타입·공간·형태 선택의 일관성과 실제 구현 대응 | 25% |
| 상호작용 상태·반응형·접근성 결정의 충분성 | 20% |
| 가정·추론·한계·희생을 구현자가 구분하고 그 영향을 설명하는가 | 15% |
| 다른 구현자가 화면을 재현·변경할 수 있는 운영 가능성 | 15% |

공통 앵커는 `0=해당 항목에 사용할 내용 없음 또는 구현과 정면 모순`, `1=단편`,
`2=핵심 일부`, `3=대부분 구체적`, `4=구체적이고 구현과 모순 없음`이다. 항목 1은
스냅샷 관찰뿐 아니라 pack이 문서에서 밝힌 자기 방법·입력에서 결정으로 이어지는 연결도
동일하게 인정한다. 항목 4는 추론이라고 명시했다는 이유로 0점을 주지 않고, 가정·추론의
범위와 구현 영향이 얼마나 유용하게 설명됐는지를 본다. **값이나 설명을 생략한 사실
자체에는 점수를 주지 않는다.** 기본값을 사용한 완전한 시스템 문서는 그 선택의 일관성·
구현 대응·운영 가능성에 따라 항목 2·3·5와 해당되는 1·4에서 점수를 받을 수 있고, 빈
문서는 각 항목에 사용할 내용이 없어 0점이다. Core v2 준수, frontmatter, 절 번호,
`evidence.*`, decision ID, 파일명, omd book 연결은 점수에 들어가지 않는다. 구현은
완성했지만 문서를 안 내면 이 축만 0점이며 run 전체 abandon은 아니다.

### 4.5 `N/A-ceiling` 재정규화와 macro-average

레인 `l`의 원래 축 가중치를 `w_{l,k}`, run 축 점수를 `S_{b,a,r,k}`, 해당 브랜드에서
사용 가능한 축 집합을 `A_b`라 한다. 보통 `A_b`는 네 축 전부이고, `N/A-ceiling` 브랜드는
식별력만 제외한 세 축이다. abandon이 아닌 run의 재정규화 총점은 다음과 같다.

`T_{l,b,a,r} = [Σ_{k∈A_b} w_{l,k} S_{b,a,r,k}] / [Σ_{k∈A_b} w_{l,k}]`

abandon run은 §7에 따라 `T=0`이며 재정규화로 복구하지 않는다. 브랜드 총점과 레인 총점은
각각 `Tbar_{l,b,a}=(1/4)Σ_r T_{l,b,a,r}`,
`Tbar_{l,a}=(1/9)Σ_b Tbar_{l,b,a}`다.

축 `k`의 PASS 입력은 먼저 브랜드 평균
`Sbar_{b,a,k}=(1/4)Σ_r S_{b,a,r,k}`를 만들고, 그 축이 가능한 브랜드 집합
`B_k={b | k∈A_b}`만 분모로 쓰는
`M_{a,k}=[Σ_{b∈B_k} Sbar_{b,a,k}]/|B_k|`다. 따라서 일부 브랜드가 식별력
`N/A-ceiling`이면 식별력의 `>=60` 판정에는 나머지 브랜드의 `M_{a,식별력}`을 넣는다.
`|B_k|=0`일 때만 그 축의 60점 조건을 면제하고 `N/A`로 보고한다. 다른 세 축의 분모는
항상 9개 브랜드이며, 결측 산출물·abandon의 0점은 가능한 축의 분모에서 빠지지 않는다.

## 5. Grok Imagine 4변형 선택 규칙

레인 A에서 프롬프트 한 번이 내는 4변형은 생성 API/UI가 표시한 순서를 `v1..v4`로 저장한다.
사후 best-of-4 선택을 금지하고, **반복 1은 v1, 반복 2는 v2, 반복 3은 v3, 반복 4는 v4**를
대표 이미지로 채점한다. 네 장 모두 원본과 hash를 보존하지만 나머지 세 장은 공통 점수에
넣지 않는다. 품질 수정으로 두 번째 batch를 만들었다면 두 번째 batch의 같은 위치를
채점하고 첫 batch도 폐기하지 않는다. 변형 순서가 확인되지 않으면 그 batch는 도구 결측으로
세 arm 모두 다시 실행한다.

레인 B에서는 각 pack이 자기 워크플로로 최종 선언한 대표 이미지 한 장을 채점한다.
대표 선언 시각과 hash는 블라인드 공개 전에 고정하며, 평가자가 보고 고를 수 없다.

## 6. 질문, 턴·시간·재시도 예산

### 레인 A

- run당 arm별 assistant completion은 **최대 6턴**이다. brief 전달은 세지 않고,
  clarification 요청·구현 보고·자기검수·수정·최종 보고는 각각 1턴이다.
- 경과 시간은 brief 전달부터 최종 hash 고정까지 **45분**이다. 생성 서비스 queue 시간도
  포함한다. 세 arm 모두에 영향을 준 공급자 장애만 block 전체 중단 사유다.
- Grok Imagine은 **초기 batch 1회 + 품질 수정 batch 1회**까지 허용한다. 품질 수정은
  실패 retry가 아니라 예산 내 revision이며 수정 이유를 기록한다.
- HTTP/전송/다운로드 실패는 동일 payload로 **1회만** retry한다. prompt나 seed를 바꾸면
  전송 retry가 아니라 품질 수정 batch를 소비한다. 그 뒤 실패하면 abandon이다.
- 코드·문서 작업도 첫 구현 뒤 **수정 1회**만 허용한다. 평가자 피드백은 받지 않는다.

### hallmark 질문 처리

질문은 **허용한다.** hallmark의 기본 design-context gate를 제거하지 않는다. 모든 arm이
질문할 수 있지만 최초 clarification 한 batch만 허용하며 위 6턴에 포함한다. 답은 항상
다음 고정문이다.

> 추가 선호 정보는 제공하지 않는다. 잠긴 브리프와 스냅샷에서 확인되는 사실만 사용하고,
> 확인되지 않은 값의 처리를 포함한 나머지 선택은 해당 pack의 기본 방법론으로 결정하라.

침묵을 “다른 브리프”나 결측으로 보지 않는다. 침묵한 arm도 동일한 잠긴 브리프를 이미
받았고 clarification 기회를 쓰지 않은 것이다. 질문한 arm에도 새 브랜드 사실·취향·해석은
주지 않으므로 입력 정보량은 늘지 않는다. 두 번째 질문은 같은 고정문으로 답하되 turn을
소비하고, 예산이 끝나면 진행 실패로 처리한다.

### 레인 B

네이티브 경로를 훼손하지 않도록 tool·생성기·내부 단계 수는 pack 기본값을 허용한다.
다만 run당 60분, clarification 한 batch, 사람 피드백 0회, 전송 실패 동일 payload retry
1회라는 외부 예산은 공통이다. 품질을 이유로 한 재생성·수정 횟수는 pack이 스스로 종료한
최종 결과까지 허용하되 모든 중간 결과와 시간을 기록한다.

## 7. 동률·결측·abandon

### 결측

- **입력 결측**: snapshot SHA 불일치, eligible 수치 필드 2개 미만, 잘못된 URL/표면은
  arm을 실행하지 않는다. 세 arm block 전체를 새 repetition ID로 교체한다.
- **평가자 결측**: 결원은 사전 등록 예비 평가자가 해당 배치 전체를 다시 채운다. 끝내
  5명을 확보하지 못하면 해당 레인은 판정하지 않는다.
- **부분 산출물 결측**: 실행 화면은 있으나 디자인 문서만 없으면 문서 축 0점이다.
  대표 이미지가 없으면 근거 추종·식별력은 0점이고 첫 렌더 결함은 실제 화면으로 센다.
- **측정 결측**: evidence에서 원래 absent인 최소 필드는 제외한다. arm 산출물 오류로
  eligible 필드를 측정 못 하면 해당 필드 0점이다. 공통 verify 도구 오류는 block 보류다.

### abandon

시간·턴·retry 예산 안에 지정 route의 첫 렌더를 만들지 못하거나 arm이 진행을 거절하면
`abandon`이다. abandon은 삭제하지 않고 해당 run 총점 **0점**, 완료율 분모에 포함한다.
정책상 정직한 거절이라는 설명은 별도 기록하되 점수를 복구하지 않는다. 공급자 전체 장애,
입력 오류, 평가 인프라 오류처럼 arm에 귀속되지 않는 실패만 세 arm block을 무효화하고
blind 해제 전에 재실행한다.

### 동률

arm 간 차이는 브랜드를 1차 군집, 그 안의 4회 **run 점수**를 2차 군집으로 한 paired
bootstrap 10,000회로 95% CI를 구한다. 식별력에서 재표집되는 값은 run별
`g_{b,a,r}`에서 계산한 `I_{b,a,r}`이며, 브랜드 보정 상수 `C_b`는 해당 브랜드 표본에
붙은 채 한 번만 적용되고 네 개의 반복 관측치로 복제되지 않는다. top arm이 아래 통과
조건을 만족하면서 runner-up보다
**5.0점 이상** 높고 차이의 95% CI 하한이 `> 0`일 때만 해당 레인의 단독 우승이다.
5.0점 미만이거나 CI가 0을 포함하면 `NO DECISIVE WINNER`다. 원점수가 같으면 공동순위로
기록하되 임의 tie-break를 하지 않는다.

## 8. 통과 임계값

arm이 한 레인에서 `PASS`하려면 다음을 모두 만족해야 한다.

1. 레인 가중 총점 `>= 75.0/100`.
2. §4.5의 축 macro-average `M_{a,k}` 각각 `>= 60.0/100`. 식별력 천장 때문에
   `|B_k|=0`인 축만 면제한다.
3. 36 run 중 abandon이 3개 이하, 즉 완료율 `>= 91.7%`, 그리고 어떤 브랜드도 4회
   모두 abandon하지 않는다.
4. 첫 렌더 `P0`가 36 run 중 1개 이하(`<= 2.8%`)다.
5. §3의 평가자 일치도 최소 기준을 모두 통과한다.

통과한 arm이 없어도 가장 높은 arm을 승자로 승격하지 않는다. 단독 우승은 `PASS`와
§7의 5점·bootstrap 조건을 모두 만족해야 한다. 레인 A와 B가 서로 다른 arm을 가리키면
그대로 두 개의 결론을 보고한다.
